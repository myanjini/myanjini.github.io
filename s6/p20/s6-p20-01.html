파일 업로드와 저장 전략

이 파트의 학습 목표파일 업로드 API를 안전하게 구현하고 응답 뒤에 실행할 작업을 등록할 수 있습니다.

지금까지는 요청 본문이 모두 JSON이었습니다. 이미지 같은 파일은 다른 형식으로 보내고, 받은 파일은 검사한 뒤 안전한 이름으로 저장해야 합니다.

파일을 보내는 형식: multipart

JSON은 글자만 담을 수 있어 이미지 같은 이진 데이터를 그대로 넣을 수 없습니다. 파일은 multipart/form-data 형식으로 보냅니다. 본문을 여러 칸(part)으로 나눠 칸마다 이름과 내용을 담는 형식으로, 웹 페이지의 파일 첨부 버튼이 쓰는 방식입니다. 로그인 폼을 읽을 때 쓴 python-multipart가 이 형식도 읽습니다.

FastAPI에서는 매개변수 타입을 UploadFile로 적으면 됩니다.

속성내용믿어도 되나요
file.filename올린 사람 컴퓨터의 파일 이름. 예: my cover.PNG아니요. 보내는 쪽이 마음대로 정합니다.
file.content_type보내는 쪽이 밝힌 형식. 예: image/png아니요. 보내는 쪽이 마음대로 정합니다.
file.size받은 파일의 크기(바이트)서버가 받은 만큼 센 값입니다.
file.file파일 내용을 읽는 객체. read()로 읽습니다.내용 자체입니다.

받기 전에 검사할 것

검사방법실패하면
형식확장자를 허용 목록(.jpg, .jpeg, .png)과 비교합니다. 금지 목록이 아니라 허용 목록을 씁니다.415 Unsupported Media Type
크기한도(2MB)보다 1바이트 더 읽어 보고, 더 읽혔으면 거절합니다.413 Content Too Large
빈 파일읽은 내용이 비었는지 봅니다.422

허용 목록을 쓰는 이유는 막아야 할 형식을 빠짐없이 나열하기가 불가능하기 때문입니다. 크기 검사에서 파일 전체를 읽지 않는 이유는, 누군가 1GB 파일을 보내면 그만큼 메모리를 쓰게 되기 때문입니다.

확장자 검사만으로는 부족합니다

확장자는 파일 이름만 바꾸면 위조할 수 있습니다. 실행 파일의 이름을 cover.png로 바꿔 올리면 확장자 검사는 통과합니다. 파일 내용의 첫 부분을 보고 정말 이미지인지 확인하는 방법은 5일차 보안 단원(S9-P31)에서 추가합니다.

저장 전략

파일 이름은 서버가 새로 짓습니다. 올린 사람이 정한 이름을 그대로 쓰면 문제가 생깁니다.

  • 두 사람이 cover.png를 올리면 뒤 파일이 앞 파일을 덮어씁니다.
  • ../../app/main.py처럼 경로 문자가 든 이름으로 다른 폴더의 파일을 덮어쓰려는 공격이 가능합니다.
  • 한글, 공백, 특수 문자가 든 이름은 주소로 쓰기 불편합니다.

그래서 uuid.uuid4().hex로 겹칠 일이 사실상 없는 32글자 무작위 이름을 만들고, 검사를 통과한 확장자만 붙입니다. 예: 5f0cb34f05924fb9914a647c1ea66874.png

데이터베이스에는 파일 내용이 아니라 주소만 저장합니다. 파일은 uploads/covers 폴더에 두고, 도서 행에는 /covers/5f0c...png 같은 주소만 넣습니다. 큰 데이터를 데이터베이스에 넣으면 백업과 조회가 느려지기 때문입니다.

업로드 폴더는 Git에 올리지 않습니다. 사용자가 올린 파일은 코드가 아니므로 .gitignore에 넣습니다. 서버를 여러 대로 늘리면 서버마다 폴더가 달라지는 문제가 생기는데, 8일차에는 이 폴더를 AWS S3로 옮깁니다.
