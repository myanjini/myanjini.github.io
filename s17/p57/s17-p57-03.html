API 명세와 보안 요구사항

자원과 기능을 API 목록으로 바꾸고, API마다 검증 규칙, 상태 코드, 권한을 정합니다. 이어서 주요 위협과 보안 요구사항을 확정합니다.

실습 목표메서드, URI, 상태 코드, 권한, 입력 검증 규칙을 갖춘 API 명세와 보안 요구사항을 작성할 수 있습니다.

  1. 메서드와 URI 정하기

    1일차에 배운 규칙(S1-P1-04)을 그대로 씁니다. URI에는 자원 이름(복수형)을 쓰고, 하는 일은 메서드로 나타냅니다. "참가 신청"처럼 CRUD로 딱 떨어지지 않는 기능은 하위 자원으로 바꿔 생각합니다. 참가 신청은 "모임의 참가자 목록에 나를 추가"이므로 POST /studies/{study_id}/members, 나가기는 DELETE /studies/{study_id}/members/me입니다.

  2. 상태 코드 고르기

    성공 코드 하나와, 일어날 수 있는 실패 코드를 모두 적습니다. 아래 표에서 고릅니다.

    코드언제예시
    200, 201, 204조회와 수정 성공, 생성 성공, 본문 없는 성공(삭제)모임 등록 201, 삭제 204
    401로그인이 필요한데 토큰이 없거나 잘못됨토큰 없이 모임 등록
    403로그인은 했지만 이 일을 할 권한이 없음남의 모임 수정
    404그런 자원이 없음. 또는 존재 자체를 숨겨야 하는 남의 자원없는 모임 번호
    409요청은 올바르지만 지금 상태와 충돌이미 참가함, 정원 초과
    422요청 값이 검증 규칙에 맞지 않음정원 1명, 제목 101자
    429너무 많이 시도함로그인 실패 5번 뒤

    403과 404 가운데 무엇을 쓸까요?

    남의 자원에 접근했을 때, 그 자원이 있다는 사실 자체가 공개 정보이면 403을 씁니다. 모임은 목록에서 누구나 보므로 남의 모임 수정은 403입니다. 반대로 대여 기록처럼 존재 자체가 남에게 알려지면 안 되는 자원은 404로 "없는 것처럼" 답합니다(S9-P32). 내 자원이 어느 쪽인지 명세에 적어 둡니다.

  3. 권한 표 만들기

    기능마다 "누가 부를 수 있는가"를 표로 정리합니다. 칸에는 허용이면 O, 막히면 그때의 상태 코드를 적습니다. 표로 그려 보면 빈칸, 곧 정하지 않은 권한이 눈에 띕니다.

    기능(예시)로그인 안 함로그인 사용자개설자 본인관리자
    모임 목록, 상세OOOO
    모임 등록401OOO
    모임 수정, 삭제401403OO
    참가 신청401O409(이미 참가)O
    참가자 명단401403OO

  4. 검증 규칙 적기

    요청으로 받는 모든 값에 규칙을 적습니다. 문자열은 최소와 최대 길이, 숫자는 범위, 목록 조회는 페이지 크기의 상한이 꼭 있어야 합니다. 그리고 "정의하지 않은 필드는 받지 않는다"는 규칙도 적습니다. 템플릿의 InputModel이 이 규칙을 처리하므로, owner_id나 member_count처럼 서버가 정해야 하는 값을 요청에 넣으면 422가 됩니다.

  5. 내 명세 작성

    양식의 "API 목록"과 "권한 표"를 채웁니다. 템플릿이 주는 회원가입, 로그인은 이미 적혀 있습니다. 내 자원의 API는 6~10개면 충분합니다.

  6. 보안 요구사항 확정

    어제 초안의 위협 가운데 3개 이상을 골라 양식의 "주요 위협과 보안 요구사항"에 옮기고, 확인할 테스트의 이름까지 정합니다. 테스트 이름은 test_무엇을_하면_어떻게_된다처럼 결과가 드러나게 짓습니다.
