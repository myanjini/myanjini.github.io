로그가 필요한 이유

이 파트의 학습 목표구조화된 로그와 요청 ID로 API의 동작과 오류를 추적할 수 있습니다.

서버는 사람이 지켜보지 않는 동안 일합니다. 문제가 생긴 뒤에 무슨 일이 있었는지 알 수 있는 유일한 단서가 로그입니다.

print 대신 logging

2일차 미들웨어는 print로 요청을 기록했습니다. print는 중요도를 구분할 수 없고, 운영할 때 일부만 끄거나 형식을 바꿀 수 없습니다. Python 표준 모듈 logging은 메시지마다 수준을 붙이고, 어디에 어떤 형식으로 쓸지를 한곳에서 정할 수 있습니다.

수준언제 쓰나요도서 API의 예
DEBUG개발 중 자세한 흐름. 운영에서는 보통 끕니다.실행한 SQL
INFO정상적으로 일어난 주요 사건요청 처리, 도서 대여
WARNING문제는 아니지만 살펴볼 일로그인 실패
ERROR요청 하나가 실패한 오류처리하지 못한 예외, 데이터베이스 연결 실패
CRITICAL서비스 전체가 멈출 만한 오류설정을 읽지 못해 시작 불가

설정한 수준보다 낮은 로그는 버립니다. LOG_LEVEL=WARNING으로 실행하면 INFO 로그는 남지 않습니다.

구조화 로그(JSON)

# 글자 로그: 사람이 읽기는 쉽지만, 프로그램이 값을 꺼내기 어렵습니다.
POST /loans 201 20.7ms

# 구조화 로그: 항목마다 이름이 있어 "status가 500인 로그만"처럼 찾기 쉽습니다.
{"time": "2026-11-21T05:17:36.186+00:00", "level": "INFO", "logger": "app.request", "message": "요청 처리",
 "request_id": "ad824d09a715491f", "method": "POST", "path": "/loans", "status": 201, "duration_ms": 20.7}

로그가 하루에 수만 줄 쌓이면 사람이 눈으로 읽을 수 없고, 검색 도구로 찾습니다. 8일차에 쓸 CloudWatch Logs Insights도 JSON 로그의 항목 이름으로 검색하고 집계합니다. 그래서 한 줄에 JSON 하나를 쓰는 형식을 씁니다.

로그는 표준 출력으로

오후에 업로드 기록을 logs/upload.log 파일에 썼습니다. 컨테이너에서는 파일에 쓰면 컨테이너를 지울 때 함께 사라지고, 여러 컨테이너의 파일을 모아 보기도 어렵습니다. 그래서 컨테이너 앱은 로그를 표준 출력(화면)으로 쓰고, 모으고 보관하는 일은 Docker와 클라우드에 맡깁니다. docker compose logs가 보여 주는 것이 바로 표준 출력입니다.

로그에 남기면 안 되는 정보

정보이유
비밀번호(틀린 비밀번호 포함)틀린 비밀번호는 대개 진짜 비밀번호의 오타라 거의 같습니다.
액세스 토큰, 리프레시 토큰, Authorization 헤더로그를 보는 사람이 그 사용자로 행세할 수 있습니다.
비밀 키, 데이터베이스 비밀번호서버 전체가 위험해집니다.
주민등록번호, 전화번호 같은 개인정보로그는 많은 사람이 보고 오래 보관됩니다. 꼭 필요하면 일부를 가립니다.

이 과정에서는 사용자를 이메일 대신 번호(user_id)로 기록하고, 로그인 실패도 입력한 값 없이 "실패했다"는 사실만 남깁니다. 로그 속 민감정보를 자동으로 가리는 방법은 5일차 보안 단원(S10-P35)에서 다룹니다.
