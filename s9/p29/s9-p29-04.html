도서 API에서 공격 지점 찾기

공격자는 서비스가 바깥의 값을 받아들이는 모든 곳을 노립니다. 도서 API에서 그런 곳을 빠짐없이 찾아 목록으로 만듭니다. 이 목록이 오늘 하루 점검의 지도가 됩니다.

실습 목표도서 API의 입력 지점, 인증 지점, 파일 처리 지점, 외부 연동 지점을 찾아 공격 지점 목록을 만들 수 있습니다.

1. 공격 지점의 종류

종류찾는 질문예
입력 지점사용자가 정한 값이 들어오는 곳은 어디인가?경로 변수, 쿼리 파라미터, 요청 본문, 헤더
인증 지점누구인지 확인하거나 권한을 판단하는 곳은 어디인가?로그인, 토큰 검사, 소유자 검사
파일 처리 지점파일을 받거나, 저장하거나, 내보내는 곳은 어디인가?표지 업로드, 표지 내보내기
외부 연동 지점서버가 다른 시스템에 요청하거나 명령을 실행하는 곳은 어디인가?데이터베이스, 앞으로 연결할 AWS 서비스

2. 목록 채우기

Swagger UI(/docs)와 코드를 함께 보며 표를 채웁니다. 칸마다 그 API에서 해당하는 것을 짧게 적고, 없으면 비워 둡니다.

API입력 지점인증 지점파일 처리외부 연동
POST /auth/signup본문: email, password없음(누구나)DB에 쓰기
POST /auth/token폼: username, password비밀번호 확인, 토큰 발급DB 읽기
GET /books쿼리: q, author_id, sort, skip, limit없음(누구나)DB 읽기(검색어가 SQL로)
PATCH /books/{book_id}경로: book_id, 본문: 바꿀 필드토큰, 소유자 검사DB 쓰기
POST /books/{book_id}/cover경로, 파일 이름, 파일 내용, 크기토큰, 소유자 검사검사, 저장, 이전 파일 삭제파일 시스템, 로그
GET /covers/...경로: 파일 이름없음(누구나)파일 내보내기파일 시스템
POST /loans본문: book_id토큰DB 쓰기(재고 변경)
POST /loans/{loan_id}/return경로: loan_id토큰, 본인 확인DB 쓰기

헤더(Authorization)도 입력 지점입니다. 공격자는 토큰을 위조하거나 지우고 보낼 수 있습니다. 표지 업로드처럼 입력, 인증, 파일 처리가 모두 겹치는 곳이 가장 먼저 점검할 곳입니다.

3. 공격자의 눈으로 질문하기

질문 1. 위 목록에서 "사용자가 보낸 값이 SQL, 파일 경로, HTML 화면 중 하나로 흘러가는 곳"을 모두 골라 보세요. 그 값을 그대로 쓰면 어떤 일이 생길 수 있을까요?

예시 답안 보기

검색어(q), 정렬 기준(sort)은 SQL로, 업로드 파일 이름과 표지 주소는 파일 경로로, 도서 제목은 웹 화면의 HTML로 흘러갑니다. 그대로 쓰면 각각 SQL 삽입, 경로 조작, 크로스사이트 스크립트가 될 수 있습니다. 지금 코드는 ORM과 허용 목록, 무작위 파일 이름 덕분에 대부분 막혀 있는데, 오늘은 이 방어가 없을 때 무슨 일이 생기는지 재현하고, 새 기능을 추가하면서 같은 실수를 하지 않는 방법을 익힙니다.

질문 2. 번호(book_id, loan_id)를 받는 API에서 공격자가 해 볼 만한 일은 무엇일까요?

예시 답안 보기

번호를 1, 2, 3처럼 바꿔 가며 남의 데이터를 읽거나 고치려고 시도할 수 있습니다. 서버가 "로그인했는가"만 확인하고 "이 데이터의 주인인가"를 확인하지 않으면 그대로 뚫립니다. OWASP API 목록의 1위인 객체 수준 인가 취약이 이것이며, S9-P32에서 다룹니다.
