응답 필드와 입력 필드 최소화

인가는 데이터와 기능뿐 아니라 필드 단위로도 필요합니다. 응답에 나가는 필드와 요청으로 받는 필드를 꼭 필요한 만큼으로 줄입니다.

실습 목표응답 모델로 내부 필드 노출을 막고, extra="forbid"로 정의하지 않은 입력 필드를 거절할 수 있습니다.

  1. 보내면 안 되는 필드를 보내 보기

    요청지금 결과내 결과
    POST /auth/signup {"email": "evil@example.com", "password": "practice-pass-9", "role": "admin"}201, "role": "user"
    PATCH /books/(내 도서) {"owner_id": 999, "price": 1500}200, owner_id는 그대로, 가격만 바뀜

    지금은 모르는 필드를 조용히 버리므로 안전합니다. 하지만 누군가 관리자 화면을 만들며 UserCreate에 role을 추가하면, 그 순간 회원가입으로 관리자가 될 수 있습니다. 요청 본문을 모델에 그대로 넣는 이런 공격을 대량 할당(mass assignment)이라고 합니다. 또 조용히 버리면, 클라이언트가 필드 이름을 잘못 보냈을 때 아무 오류 없이 무시되어 원인을 찾기 어렵습니다.

  2. 정의하지 않은 필드를 거절하기

    요청 본문 모델의 공통 부모를 만들고, 요청 본문으로 쓰는 모델이 모두 이것을 상속하게 합니다.

    app/schemas.py
    class InputModel(BaseModel):
    """요청 본문 모델의 공통 부모. 정의하지 않은 필드가 오면 422로 거절합니다."""

    model_config = ConfigDict(extra="forbid")
    app/schemas.py
    class UserCreate(InputModel):
class RefreshRequest(InputModel):
class AuthorCreate(InputModel):
class BookCreate(InputModel):
class BookUpdate(InputModel):
class StockChange(InputModel):
class LoanCreate(InputModel):

    InputModel은 UserCreate보다 위에 둡니다. 응답 모델(UserRead, BookRead 등)은 데이터베이스 객체에서 필요한 필드만 골라 읽어야 하므로 바꾸지 않습니다.

    요청기대하는 결과내 결과
    위의 회원가입 요청422, "type": "extra_forbidden", "loc": ["body", "role"]
    위의 도서 수정 요청422
    {"price": 1600}만 보낸 수정200

  3. 응답 필드 점검

    응답 모델마다 "이 필드를 받는 사람이 정말 알아야 하는가"를 따져 봅니다.

    응답 모델필드판단
    UserReadid, email, role비밀번호 해시가 없습니다. 3일차에 입력과 출력 모델을 나눈 덕분입니다.
    LoanReaduser_id 포함이제 본인과 관리자만 보므로 괜찮습니다.
    BookReadowner_id 포함누구나 봅니다. 등록자 번호가 공개되어도 되는지 업무 담당자와 정합니다. 숨기려면 공개용과 관리자용 응답 모델을 나눕니다.

    응답 모델을 빼면

    경로 함수에서 response_model을 빼고 데이터베이스 객체를 그대로 돌려주거나 user.__dict__를 응답하면, 나중에 모델에 추가한 내부 필드까지 그대로 나갈 수 있습니다. 응답은 항상 응답 모델을 거치게 합니다.
