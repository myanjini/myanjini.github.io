다른 사용자 데이터 조회 재현

def get_loan(db: Session, user: User, loan_id: int) -> Loan:
    loan = loan_repo.get(db, loan_id)
    if loan is None:
        raise AppError(404, "LOAN_NOT_FOUND", f"{loan_id}번 대여 기록을 찾을 수 없습니다.")
    return loan  # 위험한 코드: 로그인만 확인하고, 누구의 대여인지는 확인하지 않았습니다.

로그인은 확인합니다(CurrentUserDep). 하지만 서비스 함수는 user를 받기만 하고 쓰지 않습니다.

공격

user3으로 로그인한 공격자가 번호를 1부터 차례로 바꿔 요청합니다.

GET /loans/1   Authorization: Bearer (user3의 토큰)
GET /loans/2   Authorization: Bearer (user3의 토큰)
...
200 {"id": 2, "user_id": 1, "book": {"id": 18, "title": "보안 실습 도서"}, "loaned_at": "...", "returned_at": null}

user3은 user1이 어떤 책을 언제 빌렸는지 모두 볼 수 있습니다. 도서관의 대여 기록은 개인의 관심사와 생활을 드러내는 민감한 정보입니다. 번호를 1부터 끝까지 바꿔 보면 모든 사용자의 대여 기록을 모을 수 있습니다.

고치는 방향

app/services/loans.py
def find_accessible_loan(db: Session, user: User, loan_id: int) -> Loan:
    """본인이나 관리자가 볼 수 있는 대여 기록만 돌려줍니다. 남의 기록은 없는 것처럼 404로 답합니다."""
    loan = loan_repo.get(db, loan_id)
    if loan is None or (loan.user_id != user.id and user.role != "admin"):
        raise AppError(404, "LOAN_NOT_FOUND", f"{loan_id}번 대여 기록을 찾을 수 없습니다.")
    return loan


def get_loan(db: Session, user: User, loan_id: int) -> Loan:
    return find_accessible_loan(db, user, loan_id)
결정이유
남의 기록은 403이 아니라 404403은 "그 번호의 기록이 있다"는 사실을 알려 줍니다. 대여 기록처럼 존재 자체가 개인정보인 데이터는 없는 것처럼 답합니다. 3일차 S5-P17-04에서 생각해 본 질문의 답입니다.
없는 번호와 남의 번호의 응답을 똑같이메시지까지 같아야 응답을 비교해 존재를 알아낼 수 없습니다.
검사를 함수 하나로 모음상세 조회와 반납이 같은 함수를 쓰면, 한쪽만 고치고 다른 쪽을 빠뜨리는 일이 없습니다.

3일차에 만든 반납 API는 남의 기록에 403을 돌려주었습니다. 이번에 같은 함수로 바꾸면서 404로 통일합니다.
