SSH와 Session Manager 비교

리눅스 서버에 접속하는 전통적인 방법은 SSH입니다. 이 과정에서 SSH 대신 Session Manager를 쓰는 이유를 비교해 정리합니다.

SSHSession Manager
인증 수단키 페어(개인 키 파일)내 IAM 권한(콘솔이나 CLI 로그인)
열어야 하는 포트인바운드 22번없음(서버가 AWS로 먼저 연결)
관리 부담개인 키를 나눠 주고, 보관하고, 사람이 떠나면 서버마다 키를 지워야 함IAM에서 권한을 빼면 바로 접속할 수 없음
키가 새면키를 가진 누구나 접속(22번이 열려 있는 한)새는 키가 없음
누가 언제 접속했나서버 로그를 따로 모아야 함CloudTrail에 세션 시작 기록이 남고, 설정하면 입력한 명령까지 S3나 CloudWatch에 남길 수 있음
접속 경로인터넷에서 서버로 직접AWS 콘솔이나 CLI를 거쳐서

22번 포트를 0.0.0.0/0에 열어 둔 서버는 몇 분 안에 전 세계에서 비밀번호와 키 대입 시도를 받습니다. KISA 가이드의 "반복된 인증시도 제한 기능 부재"를 서버 수준에서 겪는 셈입니다. Session Manager를 쓰면 공격받을 포트 자체가 없어집니다.

Session Manager에도 주의할 점은 있습니다. 세션을 시작할 수 있는 IAM 권한이 곧 서버의 관리자 권한(sudo)이 되므로, 그 권한을 꼭 필요한 사람에게만 줍니다. 그리고 세션이 열린 브라우저 탭을 그대로 두고 자리를 비우지 않습니다. 세션은 일정 시간(기본 20분) 동안 입력이 없으면 자동으로 끊깁니다.

Session Manager를 쓰는 서버의 보안 그룹에 꼭 필요한 인바운드 규칙은 무엇인가요?

서버의 에이전트가 AWS로 먼저 연결을 맺으므로 인바운드 규칙이 필요 없습니다. 필요한 것은 아웃바운드 HTTPS입니다.
