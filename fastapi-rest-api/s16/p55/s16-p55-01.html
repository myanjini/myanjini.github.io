장애 대응 절차

이 파트의 학습 목표로그로 장애 원인을 찾고 이전 버전으로 롤백할 수 있습니다.

장애는 언젠가 반드시 일어납니다. 중요한 것은 빨리 알아채고, 피해를 먼저 멈추고, 같은 일이 다시 생기지 않게 배우는 것입니다. 이를 위한 기본 절차를 정리합니다.

단계할 일도서 API에서의 도구
1. 탐지문제가 있다는 것을 알아챕니다. 사용자 신고보다 먼저 알아채는 것이 목표입니다.CloudWatch 경보 메일, 배포 워크플로의 확인 단계 실패, ALB 대상 상태
2. 영향 확인누가, 무엇을, 얼마나 못 쓰는지 봅니다. 그에 따라 심각도를 정하고 알릴 사람에게 알립니다.ALB로 주요 API 호출, Logs Insights의 상태 코드 집계
3. 복구원인을 다 알기 전이라도 서비스를 먼저 살립니다. 가장 빠른 방법은 대개 "직전 정상 상태로 되돌리기"입니다.이전 이미지 태그로 롤백, Parameter Store 이전 버전, RDS 시점 복원
4. 원인 분석복구한 뒤 차분히 원인을 찾습니다. 직접 원인과 함께, 왜 그것이 운영까지 왔는지도 봅니다.CloudWatch Logs, 배포 기록(Actions, Run Command), Git 커밋
5. 기록과 재발 방지시간순으로 무슨 일이 있었는지 적고, 재발을 막을 일을 정합니다. 사람을 탓하지 않고 절차와 장치를 고칩니다.장애 대응 기록 양식

복구가 원인 분석보다 먼저인 이유

서비스가 멈춘 동안 원인을 찾느라 30분을 쓰면, 사용자는 30분 동안 서비스를 못 씁니다. 직전 버전으로 되돌리는 데 1분이 걸린다면 먼저 되돌리고, 원인은 그 뒤에 찾습니다. 이 과정에서 이미지를 태그 변경 불가로 버전마다 남기고(S14-P48), 비밀 값에 버전 기록을 두고(S14-P47), RDS 자동 백업을 켠 것(S13-P46)은 모두 "빨리 되돌릴 수 있게" 해 둔 준비입니다.

시간을 재는 두 숫자

용어뜻줄이는 방법
탐지까지 걸린 시간(MTTD)장애가 시작되고 알아챌 때까지경보, 배포 후 자동 확인, 헬스 체크
복구까지 걸린 시간(MTTR)알아채고 서비스가 정상으로 돌아올 때까지롤백 절차를 미리 정해 두고 연습하기, 버전별 이미지 보관

이번 실습에서도 두 시간을 기록합니다. 처음에는 길게 나오는 것이 정상입니다. 연습할수록 줄어듭니다.
