대응 과정 돌아보기

대응을 마쳤으면 돌아봅니다. 질문에 먼저 내 답을 적고 예시 답안과 비교합니다. 정답은 하나가 아니며, 내 서비스에 맞는 개선을 고르는 것이 목표입니다.

질문 1. 시나리오 A를 더 빨리 알아챌 방법은 무엇인가요?

예시 답안 보기

(1) ALB 대상 그룹의 UnHealthyHostCount가 1 이상이면 울리는 CloudWatch 경보를 더합니다. 지금의 CPU와 상태 검사 경보는 이 장애를 잡지 못합니다. (2) 배포 워크플로가 실패하면 GitHub 알림(메일)을 받도록 설정합니다. (3) 배포 직후 확인에 /health뿐 아니라 로그인 같은 핵심 API 하나를 더 호출합니다.

질문 2. 시나리오 A가 운영까지 가지 않게 막을 방법은 무엇인가요?

예시 답안 보기

배포 워크플로에서 이미지를 만든 직후, 러너 안에서 그 이미지를 실행해 /health를 확인하는 단계를 둡니다(컨테이너 시험). Dockerfile도 코드이므로 리뷰 대상에 포함합니다. 서버가 두 대 이상이면 한 대에 먼저 배포해 확인하고 나머지에 배포하는 방식(점진 배포)으로 피해를 줄일 수 있습니다.

질문 3. 복구 시간을 줄일 방법은 무엇인가요?

예시 답안 보기

롤백 절차를 명령 몇 줄의 문서나 스크립트로 정리해 두고, 워크플로에 "이전 태그로 배포"를 수동 실행 입력(workflow_dispatch의 입력값)으로 만들면 서버에 접속하지 않고 버튼으로 되돌릴 수 있습니다. 배포할 때마다 직전 태그를 기록해 두면 "어느 태그로 되돌릴지" 찾는 시간도 줄어듭니다.

질문 4. 시나리오 B에서 사용자가 겪는 시간을 줄이려면 암호 교체 절차를 어떻게 바꿔야 하나요?

예시 답안 보기

바꾼 값을 운영에 적용하기 전에 확인하는 단계를 둡니다. 예를 들어 새 값으로 일회용 컨테이너를 띄워 alembic current로 연결을 시험한 뒤에 운영 컨테이너를 다시 시작합니다. 또는 S14-P47-04에서 본 것처럼 DB 계정 두 개를 번갈아 쓰거나 Secrets Manager의 자동 교체를 씁니다.

질문 5. 이번 대응 기록에서 "사람을 탓하지 않는 기록"이 중요한 이유는 무엇인가요?

예시 답안 보기

실수한 사람을 탓하면 다음부터 실수를 숨기게 되고, 같은 함정에 다른 사람이 또 빠집니다. "포트를 잘못 바꿨다"보다 "Dockerfile 변경을 확인하는 단계가 없었다"로 적어야 장치를 고칠 수 있습니다.
