재발급 흐름 보기

로그인부터 로그아웃까지 두 토큰이 어떻게 오가는지 흐름으로 보고, 그 흐름을 만드는 코드를 강사 화면으로 봅니다.

전체 흐름

3번에서 클라이언트는 사용자에게 비밀번호를 묻지 않고 조용히 재발급을 요청한 뒤, 실패했던 요청을 새 액세스 토큰으로 다시 보냅니다. 사용자는 토큰이 바뀐 줄도 모릅니다. 리프레시 토큰까지 만료되었거나 로그아웃으로 취소되었다면 그때 로그인 화면을 보여 줍니다.

리프레시 토큰 테이블

app/models.py
class RefreshToken(Base):
    __tablename__ = "refresh_tokens"

    id: Mapped[int] = mapped_column(primary_key=True)
    user_id: Mapped[int] = mapped_column(ForeignKey("users.id"))
    # 토큰 원문이 아니라 SHA-256 해시(64글자)를 저장합니다.
    token_hash: Mapped[str] = mapped_column(String(64), unique=True)
    expires_at: Mapped[datetime]  # 만료 시각(UTC)
    revoked: Mapped[bool] = mapped_column(default=False)  # True면 더는 쓸 수 없는 토큰

로그인할 때마다 한 행이 생깁니다. 같은 사용자가 노트북과 휴대폰에서 각각 로그인하면 행이 두 개가 되고, 한쪽에서 로그아웃해도 다른 쪽은 그대로 쓸 수 있습니다.

시점행의 상태
로그인revoked=False, expires_at은 14일 뒤
재발급에 사용이 행은 revoked=True로 바뀌고, 새 토큰의 행이 하나 더 생깁니다.
로그아웃revoked=True
14일이 지남행은 남아 있지만 expires_at이 지나 쓸 수 없습니다.

발급 함수

app/security.py
def create_refresh_token() -> str:
    """추측할 수 없는 무작위 문자열을 만듭니다. JWT가 아닌 평범한 문자열입니다."""
    return secrets.token_urlsafe(32)


def hash_token(token: str) -> str:
    """리프레시 토큰을 데이터베이스에 저장하고 찾을 때 쓰는 SHA-256 해시를 만듭니다."""
    return hashlib.sha256(token.encode()).hexdigest()
app/routers/auth.py
def issue_tokens(db: Session, user: User) -> dict:
    """액세스 토큰과 리프레시 토큰을 함께 발급합니다. 리프레시 토큰은 해시만 저장합니다."""
    refresh_token = create_refresh_token()
    db.add(RefreshToken(
        user_id=user.id,
        token_hash=hash_token(refresh_token),
        expires_at=datetime.now(timezone.utc) + timedelta(days=settings.refresh_token_expire_days),
    ))
    db.commit()
    return {
        "access_token": create_access_token(user.id),
        "refresh_token": refresh_token,  # 원문은 이 응답에서 한 번만 내보냅니다.
        "token_type": "bearer",
    }

로그인 API는 마지막 줄만 return issue_tokens(db, user)로 바꿉니다. 리프레시 토큰 원문은 응답으로 딱 한 번 나가고, 서버에는 해시만 남습니다.

재발급과 로그아웃

app/routers/auth.py
@router.post("/refresh", response_model=Token, summary="토큰 재발급",
             responses={401: {"description": "리프레시 토큰이 유효하지 않음"}})
def refresh(db: SessionDep, body: RefreshRequest):
    stored = db.scalar(select(RefreshToken).where(
        RefreshToken.token_hash == hash_token(body.refresh_token),
        RefreshToken.revoked.is_(False),
        RefreshToken.expires_at > datetime.now(timezone.utc),
    ))
    if stored is None:
        raise AppError(401, "INVALID_REFRESH_TOKEN", "리프레시 토큰이 유효하지 않거나 만료되었습니다.")
    stored.revoked = True  # 한 번 쓴 리프레시 토큰은 다시 쓰지 못하게 합니다.
    user = db.get(User, stored.user_id)
    return issue_tokens(db, user)  # 새 토큰 저장과 함께 위의 변경도 commit됩니다.


@router.post("/logout", status_code=status.HTTP_204_NO_CONTENT, summary="로그아웃")
def logout(db: SessionDep, body: RefreshRequest):
    stored = db.scalar(select(RefreshToken).where(RefreshToken.token_hash == hash_token(body.refresh_token)))
    if stored is not None:
        stored.revoked = True
        db.commit()
    # 없는 토큰이어도 204를 돌려줍니다. 로그아웃은 몇 번을 해도 결과가 같아야 합니다.
코드하는 일
where(...)의 세 조건해시가 같고, 취소되지 않았고, 만료되지 않은 행만 찾습니다. 셋 중 하나라도 어긋나면 같은 401입니다.
stored.revoked = True토큰 교체입니다. 방금 쓴 리프레시 토큰으로는 다시 재발급할 수 없습니다.
로그아웃의 204토큰이 없거나 이미 취소되었어도 204입니다. 결과("이 토큰은 쓸 수 없음")가 같기 때문입니다.

로그아웃해도 액세스 토큰은 남습니다

로그아웃은 리프레시 토큰만 취소합니다. 이미 발급된 액세스 토큰은 만료될 때까지(최대 15분) 계속 쓸 수 있습니다. 액세스 토큰을 짧게 만드는 이유가 여기에 있습니다. 클라이언트도 로그아웃할 때 가지고 있던 두 토큰을 모두 지웁니다.
