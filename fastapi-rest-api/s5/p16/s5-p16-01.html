JWT의 구조

이 파트의 학습 목표로그인 시 JWT 액세스 토큰을 발급할 수 있습니다.

로그인한 뒤에도 요청을 보낼 때마다 비밀번호를 보낼 수는 없습니다. 대신 로그인할 때 한 번 받은 토큰을 보여 줍니다. 이 페이지에서는 가장 널리 쓰는 토큰 형식인 JWT를 뜯어 봅니다.

토큰이란

놀이공원을 생각해 봅시다. 매표소에서 표를 확인받으면 손목 밴드를 채워 줍니다. 그다음부터는 놀이기구마다 표를 다시 보여 주지 않고 밴드만 보여 주면 됩니다. 밴드에는 오늘 날짜가 찍혀 있어서 다음 날에는 쓸 수 없습니다.

놀이공원도서 API
매표소에서 표 확인로그인: 이메일과 비밀번호 확인
손목 밴드액세스 토큰(access token)
놀이기구 앞에서 밴드 보여 주기요청 헤더에 토큰 넣기: Authorization: Bearer 토큰
밴드에 찍힌 날짜토큰의 만료 시각

Bearer는 "가지고 있는 사람"이라는 뜻입니다. 이 토큰을 가진 사람을 토큰 주인으로 인정한다는 의미여서, 토큰이 새어 나가면 그 사람인 척할 수 있습니다. 그래서 토큰은 비밀번호처럼 다룹니다.

JWT의 세 부분

JWT(JSON Web Token)는 점(.)으로 나뉜 세 부분으로 이루어진 문자열입니다. 다음은 실제 JWT입니다.

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxIiwiZXhwIjoxNzk1MzkzODAwfQ.VQITLjTKfZnBH8M7TLl1Lwj6N3Nt0_FaZ9-RnpvnS1g
부분들어 있는 것위 토큰을 풀어 보면
헤더(header)서명 방식{"alg":"HS256","typ":"JWT"}
페이로드(payload)토큰에 담은 정보. 하나하나를 클레임(claim)이라고 부릅니다.{"sub":"1","exp":1795393800}
서명(signature)헤더와 페이로드를 비밀 키로 계산한 값풀어도 의미 있는 글자가 나오지 않습니다.

위 토큰은 색으로 세 부분을 나눠 보였습니다. 헤더와 페이로드는 Base64URL이라는 방식으로 글자만 바꿔 적은 것입니다. 암호화가 아니므로 누구나 원래 JSON으로 되돌려 읽을 수 있습니다.

클레임뜻이 과정의 값
subsubject. 이 토큰의 주인사용자 번호를 문자열로: "1"
expexpiration. 만료 시각. 1970년 1월 1일부터 센 초1795393800은 2026년 11월 23일 오전 9시 30분(한국 시간)

서명이 하는 일

누구나 페이로드를 읽을 수 있다면, "sub":"1"을 "sub":"2"로 바꿔 다른 사람인 척할 수 있지 않을까요? 이것을 막는 것이 서명입니다. 서버는 토큰을 만들 때 서버만 아는 비밀 키로 헤더와 페이로드의 서명을 계산해 붙입니다. 토큰을 받으면 같은 비밀 키로 서명을 다시 계산해 붙어 온 서명과 비교합니다. 페이로드를 한 글자라도 바꾸면 계산한 서명이 달라지고, 비밀 키를 모르는 사람은 맞는 서명을 새로 만들 수 없습니다.

JWT에 넣으면 안 되는 것

서명은 "바뀌지 않았음"을 보장할 뿐 "남이 읽지 못함"을 보장하지 않습니다. 따라서 페이로드에 비밀번호, 주민등록번호, 전화번호 같은 정보를 넣으면 안 됩니다. 이 과정에서는 사용자 번호와 만료 시각만 넣습니다.

비밀 키 관리

서명에 쓰는 비밀 키는 2일차 S3-P9에서 .env의 SECRET_KEY에 넣어 둔 값입니다. 이 키가 유출되면 누구든 아무 사용자의 토큰이나 만들 수 있으므로, 서버 전체의 열쇠라고 생각해야 합니다.

  • secrets.token_hex(32)처럼 추측할 수 없는 값을 씁니다. 32바이트보다 짧으면 안전하지 않습니다.
  • .env는 Git에 올리지 않습니다. 이미 .gitignore에 넣어 두었습니다.
  • 개발용 키와 운영용 키를 다르게 씁니다. 7일차에는 운영용 키를 AWS Parameter Store에 보관합니다.
