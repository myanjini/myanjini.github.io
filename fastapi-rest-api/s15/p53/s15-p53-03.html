내 저장소에 배포 자동화 적용

내 저장소에 배포 자동화를 적용합니다. OIDC 공급자와 배포 역할을 만들고, 워크플로를 추가해 푸시하면 테스트부터 배포까지 자동으로 진행되는지 확인합니다. 일부러 테스트를 깨뜨려 배포가 멈추는 것도 확인합니다.

실습 목표OIDC 역할과 배포 워크플로를 구성하고, 푸시로 자동 배포와 실패 시 중단을 확인할 수 있습니다.

  1. OIDC 공급자 확인 또는 추가

    IAM 콘솔의 자격 증명 공급자에 token.actions.githubusercontent.com이 있는지 봅니다. 공급자는 계정에 하나만 만들 수 있으므로, 같은 계정의 다른 학생이나 강사가 이미 만들었다면 그대로 씁니다. 없으면 공급자 추가에서 다음과 같이 만듭니다.

    항목값
    공급자 유형OpenID Connect
    공급자 URLhttps://token.actions.githubusercontent.com
    대상sts.amazonaws.com

  2. 배포 역할 만들기

    IAM의 역할 생성에서 신뢰할 수 있는 엔터티 유형으로 웹 자격 증명을 고르고, 공급자 token.actions.githubusercontent.com, 대상 sts.amazonaws.com, GitHub 조직(내 아이디), 저장소(book-api), 브랜치(main)를 입력합니다. 권한은 건너뛰고, 이름은 book-api-github-deploy(공용 계정이면 식별자를 붙임), 태그 Owner를 넣어 만듭니다. 만든 뒤 신뢰 관계 탭에서 sub가 앞 페이지의 형식(repo:내아이디@아이디번호/book-api@저장소번호:ref:refs/heads/main)인지 확인합니다. 번호는 S15-P53-01의 방법으로 찾고, 마법사가 만든 값이 이 형식과 다르면 신뢰 정책 편집에서 고칩니다. 그다음 인라인 정책 book-api-deploy를 추가합니다. 계정 ID와 인스턴스 ID를 내 값으로 바꿉니다.

  3. 저장소 변수 등록

    GitHub 저장소의 Settings, Secrets and variables, Actions, Variables 탭에서 세 값을 등록합니다. 모두 비밀 값이 아닙니다.

    이름값의 예
    AWS_DEPLOY_ROLE_ARNarn:aws:iam::123456789012:role/book-api-github-deploy
    EC2_INSTANCE_IDi-0123456789abcdef0
    ALB_DNS_NAMEbook-api-alb-1234567890.ap-northeast-2.elb.amazonaws.com

  4. 워크플로 추가하고 푸시

    test.yml의 on 부분을 바꾸고, deploy.yml을 앞 페이지 그대로 만듭니다. ECR 저장소 이름이 book-api가 아니면 ECR_REPOSITORY 값을 바꿉니다.

    git add .github/workflows
git commit -m "배포 자동화"
git push

    GitHub의 Actions 탭에서 deploy 실행을 엽니다. test 작업이 끝나면 deploy 작업이 시작되고, 각 단계를 눌러 출력을 볼 수 있습니다. 배포 단계의 출력에는 서버에서 실행한 명령의 결과(이미지 받기, 마이그레이션, 컨테이너 교체)가 그대로 찍힙니다.

  5. 배포 결과 확인

    Windows에서 실행할 때

    아래 명령에는 bash 문법(이름=값, $(...) 등)이 들어 있습니다. 내 PC가 Windows라면 명령 프롬프트가 아니라 Git Bash에서 실행합니다(S12-P40-03). EC2 서버의 접속 화면에서 실행하는 명령은 그대로 입력합니다.

    cat ~/book-api/.env
IMAGE=123456789012.dkr.ecr.ap-northeast-2.amazonaws.com/book-api:git-9c2e5d1
COVER_BUCKET=book-api-covers-student07-7f3k

docker compose -f compose.prod.yaml ps --format "{{.Image}}  {{.Status}}"
123456789012.dkr.ecr.ap-northeast-2.amazonaws.com/book-api:git-9c2e5d1  Up 2 minutes (healthy)

    서버의 이미지 태그가 방금 푸시한 커밋과 같아야 합니다. Systems Manager 콘솔의 Run Command, 명령 기록에서도 "deploy 9c2e5d1" 명령과 그 출력을 볼 수 있습니다.

  6. 실패하면 멈추는지 확인

    새 브랜치에서 일부러 테스트 하나를 깨뜨려 풀 리퀘스트를 만들면, test만 실행되고 배포는 시작조차 하지 않습니다. main에 실수로 깨진 코드가 들어가는 경우도 확인합니다. 아래처럼 테스트를 깨뜨려 main에 푸시합니다.

    # tests/test_books.py의 테스트 하나에서 기대값을 일부러 틀리게 바꾼 뒤
git commit -am "실패 확인용(되돌릴 예정)"
git push

    Actions에서 test가 빨간색으로 실패하고, deploy 작업은 "건너뜀"으로 표시됩니다. 서버의 이미지 태그는 바뀌지 않았습니다. 확인했으면 바로 되돌립니다.

    git revert --no-edit HEAD
git push

    되돌린 커밋으로 다시 배포가 실행됩니다. 실패 원인을 찾을 때는 빨간 단계를 눌러 마지막 출력부터 읽습니다.
