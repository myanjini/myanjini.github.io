ALB와 대상 그룹

이 파트의 학습 목표ALB 뒤에 API를 배치하고 HTTPS 적용 과정을 설명할 수 있습니다.

ALB(Application Load Balancer)는 HTTP 요청을 받아 뒤에 있는 서버들로 나눠 보내는 관리형 로드 밸런서입니다. 서버가 한 대여도 ALB를 두면 접속 주소가 고정되고, 상태가 나쁜 서버로는 요청을 보내지 않으며, HTTPS를 서버 대신 처리할 수 있습니다.

S12-P42-03에서 미리 설계한 8일차 규칙 그대로입니다. 인터넷 전체에 열린 곳은 ALB 한 곳뿐이고, 그 뒤는 보안 그룹 참조로 한 단계씩 좁혀집니다. EC2는 패키지를 받으려고 퍼블릭 IP를 그대로 가지지만, 들어오는 길은 ALB뿐입니다.

ALB 뒤에서 달라지는 것: 진짜 사용자 IP

ALB를 두면 EC2의 앱이 보는 요청의 출발지는 사용자가 아니라 ALB(VPC 안의 10.0.x.x 주소)가 됩니다. 도서 API는 S10에서 같은 IP의 로그인 실패를 15분에 20번으로 제한했습니다. 그대로 두면 모든 사용자가 ALB의 IP 하나로 보여서, 몇 사람의 실패가 다른 사람들의 로그인까지 막아 버립니다.

ALB는 원래 사용자의 IP를 X-Forwarded-For 헤더에 붙여 넘겨줍니다. 하지만 이 헤더는 사용자도 마음대로 보낼 수 있으므로 무조건 믿으면 안 됩니다(S11의 "보안기능 결정에 사용되는 부적절한 입력값"). 그래서 uvicorn에 "VPC 안(ALB)에서 온 요청이 붙인 헤더만 믿으라"고 알려 줍니다. 운영용 Compose의 FORWARDED_ALLOW_IPS: 10.0.0.0/16이 이 설정입니다.

사용자가 보낸 헤더ALB가 넘긴 헤더앱이 보는 IP
없음X-Forwarded-For: 203.0.113.9203.0.113.9(진짜 사용자)
X-Forwarded-For: 1.2.3.4(위조)X-Forwarded-For: 1.2.3.4, 203.0.113.9203.0.113.9. uvicorn은 오른쪽부터 보면서 믿는 범위(10.0.0.0/16)가 아닌 첫 주소를 고릅니다.

실습 환경에서 같은 상황을 재현해 확인했습니다. 믿는 범위를 정하지 않으면 로그인 실패 기록의 IP가 모두 프록시 주소로 남고, 정하면 위조한 앞쪽 값이 아니라 프록시가 붙인 진짜 주소가 남습니다.

ALB 요금

ALB는 켜져 있는 시간과 처리량(LCU)에 요금이 붙고, 가용 영역마다 공용 IPv4 주소를 쓰므로 그 요금도 붙습니다. 실습이 끝나면 S18에서 가장 먼저 지웁니다.
