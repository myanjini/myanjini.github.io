좋은 URI, 나쁜 URI

REST 방식으로 URI를 설계하는 감각을 질문에 답하며 익힙니다. 답을 먼저 쓰고 예시 답안과 비교하세요.

질문 1. 다음 세 URI를 REST 원칙에 맞게 메서드와 URI로 고쳐 써 보세요.
GET /getBooks, POST /createBook, GET /deleteBook?id=3

예시 답안 보기

GET /books, POST /books, DELETE /books/3

세 URI 모두 주소에 동작(get, create, delete)이 들어 있습니다. 동작은 메서드가 맡고, 주소에는 자원 이름(books)만 남깁니다. 특히 세 번째는 삭제를 GET으로 요청하고 있어 위험합니다. 브라우저나 검색 엔진이 링크를 미리 열어 보기만 해도 데이터가 지워질 수 있기 때문입니다.

질문 2. 1번 저자가 쓴 도서 목록을 조회하는 URI를 두 가지 방법으로 써 보세요.

예시 답안 보기

GET /authors/1/books 또는 GET /books?author_id=1

앞의 방법은 "1번 저자에게 속한 도서"라는 관계를 주소로 나타냅니다. 뒤의 방법은 도서 목록에 조건을 붙여 걸러 냅니다. 둘 다 쓰이며, 이 과정에서는 검색 조건이 여러 개로 늘어나기 쉬운 쿼리 문자열 방식을 주로 씁니다.

질문 3. /Books, /book_list, /books 중 가장 일반적인 형태는 무엇이고, 이유는 무엇인가요?

예시 답안 보기

/books입니다. URI는 대소문자를 구분하므로 소문자로 통일하고, 자원 모음은 복수형 명사로 씁니다. 단어가 여러 개라면 밑줄보다 하이픈을 쓰는 것이 일반적입니다(예: /book-categories).

이 파트에서 정리한 URI 규칙

  • 주소에는 명사, 동작은 메서드로 나타냅니다.
  • 자원 모음은 복수형으로 씁니다(/books).
  • 소문자를 쓰고 단어 사이는 하이픈으로 잇습니다.
  • 조회 조건은 쿼리 문자열로 덧붙입니다.
