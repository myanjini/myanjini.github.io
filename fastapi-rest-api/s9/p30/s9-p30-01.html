입력데이터 검증 및 표현

이 파트의 학습 목표SQL 삽입과 경로 조작 보안약점을 재현하고 안전한 코드로 고칠 수 있습니다.

입력데이터 검증 보안약점은 모두 같은 원인에서 나옵니다. 바깥에서 온 값을 믿고, 그 값이 프로그램의 명령 구조에 섞여 들어가게 둔 것입니다.

외부 입력은 모두 믿지 않습니다

서버 밖에서 온 값은 모두 공격자가 마음대로 정할 수 있다고 가정합니다. 웹 화면이 막아 준다고 안심하면 안 됩니다. 공격자는 화면을 거치지 않고 curl로 직접 요청을 보냅니다.

외부 입력예
경로와 쿼리 파라미터/books/{book_id}, ?q=...&sort=...
요청 본문JSON 필드, 폼 필드
헤더와 쿠키Authorization, User-Agent
파일파일 이름, 크기, 내용, 보내는 쪽이 밝힌 형식
다른 시스템의 응답외부 API가 돌려준 값도 그 시스템이 뚫렸다면 공격자의 값입니다.

허용 목록으로 검증합니다

"이런 값은 안 된다"를 나열하는 금지 목록은 공격자가 목록에 없는 새 방법을 찾으면 뚫립니다. "이런 값만 된다"를 정하는 허용 목록이 더 안전합니다. 2일차에 정렬 기준을 Literal["id", "price", "-price"]로 제한하고, 3일차에 업로드 확장자를 정해 둔 것이 허용 목록입니다.

Pydantic 검증이 해 주는 것과 못 하는 것

해 주는 것못 하는 것
타입 확인: 숫자 자리에 글자가 오면 422"이 문자열을 SQL에 넣어도 안전한가"는 판단하지 않습니다.
길이, 범위, 형식(정규식) 제한도서 제목에 작은따옴표(')나 <script>가 들어 있어도 문자열로서는 올바른 값입니다.
허용 목록(Literal)값이 어디에 쓰이는지 모르므로, 쓰는 곳에 맞는 처리는 개발자 몫입니다.

그래서 두 겹으로 지킵니다. 받을 때는 Pydantic으로 타입, 길이, 형식을 좁히고, 쓸 때는 쓰는 곳에 맞게 처리합니다. SQL에는 값 바인딩, 파일 경로에는 기준 폴더 검사, HTML 화면에는 출력할 때의 처리, 셸 명령에는 인자 목록 전달입니다. 오늘 오전의 나머지 실습이 이 네 가지입니다.
