응답 뒤에 실행하는 작업

업로드가 끝날 때마다 기록을 남기려고 합니다. 그런데 기록을 남기는 데 시간이 걸린다면 사용자가 그만큼 기다려야 할까요? 응답을 먼저 보내고 나중에 실행하는 방법을 직접 비교합니다.

실습 목표BackgroundTasks로 응답 뒤에 실행할 작업을 등록하고, 응답 시간의 차이를 확인할 수 있습니다.

BackgroundTasks

경로 함수에 background_tasks: BackgroundTasks 매개변수를 추가하고 add_task(함수, 인자...)로 할 일을 등록하면, FastAPI가 응답을 보낸 뒤에 그 함수를 실행합니다. 알림 메일 보내기, 기록 남기기처럼 사용자가 결과를 기다릴 필요가 없는 일에 씁니다.

  1. 기록 함수 추가

    app/services/covers.py 맨 위에 import time과 from datetime import datetime을 추가하고, 맨 아래에 기록 함수를 넣습니다. 기록을 다른 서버로 보내는 데 2초가 걸린다고 가정하는 줄을 실습용으로 함께 넣습니다.

    app/services/covers.py
    def write_upload_log(book_id: int, user_id: int, original_name: str, size: int) -> None:
    """업로드 기록을 파일에 한 줄씩 남깁니다."""
    LOG_FILE.parent.mkdir(exist_ok=True)
    time.sleep(2)  # 실습용: 기록을 다른 서버로 보내는 데 2초 걸린다고 가정합니다.
    line = f"{datetime.now().isoformat(timespec='seconds')} book={book_id} user={user_id} file={original_name} size={size}\n"
    with LOG_FILE.open("a", encoding="utf-8") as f:
        f.write(line)

  2. 먼저 직접 호출해 보기

    app/routers/books.py
    def upload_book_cover(db: SessionDep, user: CurrentUserDep, book_id: int, file: UploadFile):
    book = book_service.upload_cover(db, user, book_id, file)
    covers.write_upload_log(book.id, user.id, file.filename, file.size)  # 직접 호출
    return book

    라우터 가져오기에 from app.services import covers를 추가하고 서버를 다시 시작합니다. 표지를 올리면 Execute를 누른 뒤 응답이 오기까지 2초쯤 걸립니다. 응답 헤더의 x-process-time을 적습니다. 2일차에 만든 처리 시간 미들웨어가 붙인 값입니다.

    방식x-process-time내 결과
    직접 호출약 2050ms

  3. 백그라운드로 바꾸기

    app/routers/books.py
    @router.post("/{book_id}/cover", response_model=BookRead, summary="표지 이미지 업로드",
             responses={**FORBIDDEN_OR_NOT_FOUND, 413: {"description": "2MB 초과"},
                        415: {"description": "jpg, jpeg, png가 아님"}})
def upload_book_cover(db: SessionDep, user: CurrentUserDep, book_id: int, file: UploadFile,
                      background_tasks: BackgroundTasks):
    book = book_service.upload_cover(db, user, book_id, file)
    # 응답을 보낸 뒤에 실행할 일을 등록합니다.
    background_tasks.add_task(covers.write_upload_log, book.id, user.id, file.filename, file.size)
    return book

    가져오기에 BackgroundTasks를 더하고 서버를 다시 시작한 뒤 다시 올립니다.

    방식x-process-time내 결과
    백그라운드수십 ms

    응답은 바로 오고, 약 2초 뒤에 logs/upload.log에 한 줄이 추가됩니다. 파일을 열어 확인합니다.

    logs/upload.log
    2026-11-21T13:49:34 book=6 user=1 file=my cover.PNG size=208

  4. 실습용 지연 지우기

    확인했으면 time.sleep(2) 줄과 import time을 지웁니다.

BackgroundTasks의 한계

한계설명
같은 서버 안에서 실행작업이 오래 걸리면 그만큼 서버의 힘을 씁니다. 동영상 변환처럼 무거운 작업에는 맞지 않습니다.
사라질 수 있음작업이 끝나기 전에 서버가 꺼지면 그 작업은 실행되지 않습니다. 다시 시도해 주지도 않습니다.
결과를 알려 주지 않음응답은 이미 나갔으므로 작업이 실패해도 사용자는 모릅니다.

반드시 실행되어야 하거나 무거운 작업은 작업을 줄 세워 두고 다른 프로그램이 처리하는 작업 큐(예: Celery, AWS SQS)를 씁니다. 이 과정에서는 다루지 않습니다.
