시간 및 상태와 코드오류

지금까지 다룬 보안약점은 대부분 "요청 하나"를 들여다보면 찾을 수 있었습니다. 시간 및 상태 유형은 요청 여러 개가 동시에 들어오거나 시간이 흐를 때 드러나고, 코드오류 유형은 평소에는 멀쩡하다가 드문 상황에서 터집니다.

시간 및 상태: 검사 시점과 사용 시점

프로그램은 흔히 "확인하고, 그 결과를 믿고 행동"합니다. 재고가 있는지 확인하고 재고를 줄이는 식입니다. 그런데 확인한 시점과 행동하는 시점 사이에 다른 요청이 같은 데이터를 바꾸면, 확인한 결과는 이미 사실이 아닙니다. 이 문제를 검사 시점과 사용 시점의 경쟁 조건(TOCTOU, Time Of Check to Time Of Use)이라고 합니다. 여러 요청이 같은 자원을 먼저 차지하려고 경쟁한다고 해서 경쟁 조건이라고 부릅니다.

이 문제는 요청을 하나씩 보내는 테스트로는 절대 드러나지 않습니다. 사용자가 몰리는 시간, 예를 들어 인기 도서가 들어온 날에만 나타나기 때문에 "가끔 재고가 안 맞는다"는 식의 찾기 어려운 버그가 됩니다.

상황무엇이 어긋나나요
마지막 재고를 동시에 대여재고보다 많이 빌려집니다.
좋아요 수를 읽고 1을 더해 저장동시에 누른 좋아요가 사라집니다.
쿠폰 사용 여부를 확인하고 사용 처리쿠폰 하나를 여러 번 씁니다.
잔액을 확인하고 출금잔액보다 많이 출금됩니다.

해결의 원칙은 하나입니다. 확인과 변경을 떼어 놓지 않고, 데이터베이스가 한 번에 처리하게 합니다. 다음 두 페이지에서 도서 API로 직접 재현하고 고칩니다.

시간 및 상태: 종료되지 않는 반복

끝나는 조건이 없는 반복문이나 재귀 함수는 서버의 일꾼(스레드)을 붙잡고 놓아 주지 않습니다. 이런 요청이 몇 개만 쌓여도 서버가 다른 요청에 답하지 못합니다. 실수로 자주 만드는 모양은 "성공할 때까지 다시 시도"입니다.

잘못된 예
while True:                      # 상대 서버가 계속 실패하면 끝나지 않습니다.
    try:
        return requests.get(url)
    except requests.RequestException:
        continue
바른 예
for attempt in range(3):         # 다시 시도하는 횟수에 끝을 둡니다.
    try:
        return requests.get(url, timeout=3)  # 한 번 기다리는 시간에도 끝을 둡니다.
    except requests.RequestException:
        time.sleep(0.5 * (attempt + 1))      # 조금씩 더 기다렸다가 다시 시도합니다.
raise AppError(502, "UPSTREAM_FAILED", "외부 서버에 연결하지 못했습니다.")

사용자가 반복 횟수를 정하게 하는 것도 같은 문제입니다. 도서 API는 목록 조회의 limit을 100 이하로 묶어 두었습니다(S3-P10). 한 번에 처리하는 양과 시간에 항상 상한을 둡니다.

코드오류: None 처리

KISA 가이드는 이 약점을 Null 포인터 역참조라고 부릅니다. Python에서는 값이 없음을 뜻하는 None에서 속성을 꺼낼 때 일어납니다. 조회 결과가 없으면 None이 오는데, 이를 확인하지 않고 쓰면 AttributeError나 TypeError가 나서 500 오류가 됩니다. 전역 예외 처리가 없던 시절이라면 트레이스백까지 새어 나갔을 것입니다.

잘못된 예
book = db.get(Book, book_id)     # 없는 번호면 None
return book.title                # AttributeError: 'NoneType' object has no attribute 'title'

도서 API는 처음부터 find_book에서 None을 먼저 확인하고 404를 냈습니다(S4). "없을 수 있는 값"을 돌려주는 함수(db.get, scalar_one_or_none, 딕셔너리의 get, fetchone)를 쓴 바로 다음 줄에서 확인하는 습관을 들입니다.

코드오류: 자원 해제

데이터베이스 연결, 열린 파일, 네트워크 연결은 개수가 정해진 자원입니다. 다 쓰고 닫지 않으면 조금씩 쌓이다가 어느 순간 "연결할 수 없음" 오류로 서비스가 멈춥니다. 특히 중간에 예외가 나면 닫는 코드까지 가지 못하는 경우가 많습니다.

자원도서 API에서 닫는 방법
데이터베이스 세션get_db의 try와 finally(S3). 예외가 나도 finally는 실행됩니다.
파일with open(...)(S6). 블록을 벗어나면 자동으로 닫힙니다.
외부 HTTP 연결with httpx.Client() as client:처럼 with로 씁니다.

코드오류 유형에는 이 밖에 해제된 자원 사용, 초기화되지 않은 변수 사용, 신뢰할 수 없는 데이터의 역직렬화가 있습니다. Python은 닫힌 파일을 읽거나 값을 넣지 않은 변수를 쓰면 바로 예외를 내므로 앞의 두 가지는 C 언어보다 덜 위험합니다. 역직렬화는 다음 파트(S11-P37)에서 위험한 함수와 함께 다룹니다.

다음 가운데 요청을 하나씩 보내는 테스트로는 찾기 가장 어려운 약점은 무엇인가요?

경쟁 조건은 요청 여러 개가 같은 순간에 들어올 때만 나타납니다. 그래서 동시에 요청을 보내는 시험이 따로 필요합니다.
