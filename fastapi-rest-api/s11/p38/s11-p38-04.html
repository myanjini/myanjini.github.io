진단 결과 점검

진단을 마쳤으면 바로 답을 보지 말고, 유형별 점검 질문에 스스로 답하며 놓친 약점이 없는지 한 번 더 살핍니다. 그다음 예시 진단표와 비교합니다.

실습 목표점검 질문으로 놓친 약점을 찾고, 예시 진단표와 비교해 내 진단의 빈틈을 확인할 수 있습니다.

스스로 묻고 답하기

점검 1. upload_file 함수 하나에서 찾을 수 있는 약점을 모두 적어 보세요. 몇 개인가요?

예시 답안 보기

다섯 가지입니다. 파일 이름을 그대로 경로에 쓰는 경로 조작, shell=True의 명령어 삽입, 확장자와 크기 검사가 없는 위험한 형식 파일 업로드, except Exception: pass의 오류상황 대응 부재, 로그인 검사가 없는 적절한 인증 없는 중요 기능 허용입니다. 기능이 많은 함수일수록 약점이 몰려 있습니다.

점검 2. 로그인 토큰은 어떻게 만들고 어떻게 읽나요? 거기서 생기는 문제를 두 가지 이상 적어 보세요.

예시 답안 보기

사용자 정보를 pickle로 바꾸고 Base64로 인코딩만 합니다. 서명이 없으므로 누구나 role을 admin으로 바꾼 토큰을 만들 수 있고, 만료 시각도 없습니다. 더 심각한 문제는 서버가 받은 토큰을 pickle.loads로 읽는다는 점입니다. 공격자가 만든 토큰으로 서버에서 코드를 실행할 수 있습니다(신뢰할 수 없는 데이터의 역직렬화).

점검 3. /me는 토큰을 검증하는데도 다른 사람의 이름이 나올 수 있습니다. 어떤 상황에서, 왜 그런가요?

예시 답안 보기

두 사용자가 거의 동시에 요청하면 그렇습니다. read_token이 사용자 정보를 모든 요청이 함께 쓰는 전역 딕셔너리 CURRENT_USER에 넣고, me는 0.1초 뒤에 그 딕셔너리를 읽습니다. 그 사이에 다른 요청이 값을 덮으면 다른 사람의 정보가 응답됩니다(잘못된 세션에 의한 데이터 정보노출).

점검 4. 없는 공지 번호(예: 9999)를 조회하면 응답에 무엇이 나오나요? 진단표의 몇 개 항목과 관련되나요?

예시 답안 보기

500 응답에 예외 메시지와 트레이스백(파일 경로, 코드 줄)이 담깁니다. 결과가 없을 때를 처리하지 않은 Null 포인터 역참조와, 트레이스백을 응답하는 오류 메시지 정보노출 두 항목이 겹친 결과입니다.

점검 5. link_preview에서 찾을 수 있는 약점을 모두 적어 보세요.

예시 답안 보기

세 가지입니다. 어떤 주소든 서버가 대신 요청하는 서버사이드 요청 위조, 실패하면 끝없이 다시 시도하는 종료되지 않는 반복문, 로그인 없이 쓸 수 있는 적절한 인증 없는 중요 기능 허용입니다. requirements.txt의 requests 버전에 알려진 취약점이 있는 것까지 보면 네 가지입니다.

점검 6. 코드에 적힌 SECRET_KEY는 어디에서도 토큰 서명에 쓰이지 않습니다. 그래도 약점인가요?

예시 답안 보기

약점입니다. 지금은 /debug/config로 그대로 노출되고, 나중에 누군가 서명에 쓰기 시작하면 코드를 본 사람 누구나 토큰을 위조할 수 있습니다. 코드와 Git 기록에 남은 비밀 값은 지워도 기록에서 되살릴 수 있으므로 키를 바꿔야 합니다.

예시 진단표

내 진단표와 비교한 뒤, 놓친 항목은 내 진단표에 추가합니다. 위험도는 판단하는 사람과 서비스의 상황에 따라 한 단계쯤 달라질 수 있습니다. 근거를 설명할 수 있다면 다르게 적어도 괜찮습니다. 조치 내용과 확인 방법은 다음 파트에서 채웁니다.

예시 진단표 보기(25개 항목)
번호보안약점 항목(유형)위치(app.py의 함수)와 위험도진단 근거
1SQL 삽입
(입력데이터 검증 및 표현)		list_notices
위험도 상		q, sort, limit를 f-문자열로 SQL에 이어 붙입니다. q에 %' UNION SELECT id, username, password_hash FROM users --를 넣으면 목록에 아이디와 비밀번호 해시가 섞여 나옵니다.
2경로 조작 및 자원 삽입
(입력데이터 검증 및 표현)		upload_file, download_file
위험도 상		업로드한 파일 이름을 그대로 경로에 붙여 ../escape.txt로 업로드 폴더 밖에 씁니다. /files/%2e%2e%2fboard.db로 데이터베이스 파일을 내려받습니다.
3운영체제 명령어 삽입
(입력데이터 검증 및 표현)		upload_file
위험도 상		file -b {path}를 shell=True로 실행합니다. 파일 이름을 memo.txt;touch injected로 올리면 뒤의 명령이 실행됩니다.
4위험한 형식 파일 업로드
(입력데이터 검증 및 표현)		upload_file
위험도 중		확장자와 크기를 검사하지 않아 .py, .html 같은 파일과 아주 큰 파일도 저장됩니다.
5서버사이드 요청 위조
(입력데이터 검증 및 표현)		link_preview
위험도 상		사용자가 준 url을 검사 없이 서버가 요청합니다. http://169.254.169.254/(클라우드 서버의 메타데이터 주소)나 내부 주소를 대신 조회하게 할 수 있습니다.
6보안기능 결정에 사용되는 부적절한 입력값
(입력데이터 검증 및 표현)		pin_notice
위험도 상		요청 헤더 X-Role의 값으로 관리자인지 판단합니다. 헤더는 누구나 붙일 수 있습니다.
7부적절한 인가
(보안기능)		delete_notice
위험도 상		로그인 여부만 확인하고 작성자인지는 확인하지 않아, 누구나 남의 공지를 지웁니다.
8취약한 암호화 알고리즘 사용, 솔트 없이 일방향 해쉬 함수 사용
(보안기능)		signup, login
위험도 상		비밀번호를 솔트 없는 MD5로 저장합니다. 해시가 새면 미리 계산한 표로 금방 원래 비밀번호를 찾습니다.
9취약한 비밀번호 허용
(보안기능)		SignupIn
위험도 중		비밀번호 규칙이 없어 1234로도 가입됩니다.
10반복된 인증시도 제한 기능 부재
(보안기능)		login
위험도 중		로그인 실패 횟수를 세지 않아 비밀번호를 끝없이 대입해 볼 수 있습니다.
11하드코드된 중요정보
(보안기능)		SECRET_KEY 상수
위험도 중		비밀 키가 소스 코드에 적혀 있어 코드를 본 사람은 누구나 압니다. Git 기록에도 남습니다.
12적절하지 않은 난수 값 사용
(보안기능)		password_reset
위험도 중		비밀번호 재설정 인증 번호를 random으로 만듭니다. 다음 값을 예측할 수 있고, 데이터베이스에 평문으로 저장합니다.
13적절한 인증 없는 중요 기능 허용
(보안기능)		import_notices, upload_file, link_preview
위험도 상		공지 일괄 등록, 파일 업로드, 외부 주소 요청을 로그인 없이 누구나 씁니다.
14경쟁 조건: 검사 시점과 사용 시점
(시간 및 상태)		like_notice
위험도 하		좋아요 수를 읽고, 1을 더해 저장합니다. 10명이 동시에 누르면 10보다 적게 올라갑니다.
15종료되지 않는 반복문 또는 재귀 함수
(시간 및 상태)		link_preview
위험도 중		연결에 실패하면 while True로 끝없이 다시 시도합니다. 연결되지 않는 주소 몇 개로 서버의 일꾼을 모두 붙잡아 둘 수 있습니다.
16오류 메시지 정보노출
(에러처리)		handle_error
위험도 중		처리하지 못한 예외의 메시지와 트레이스백을 응답에 담아, 파일 경로와 코드 구조가 드러납니다.
17오류상황 대응 부재
(에러처리)		upload_file
위험도 하		except Exception: pass로 파일 형식 확인의 실패를 아무 기록 없이 숨깁니다.
18Null 포인터 역참조
(코드오류)		get_notice
위험도 하		없는 번호를 조회하면 fetchone()이 None을 돌려주는데, 확인 없이 row["id"]를 꺼내 500 오류가 납니다. 16번과 겹쳐 트레이스백까지 노출됩니다.
19부적절한 자원 해제
(코드오류)		get_conn을 쓰는 모든 함수
위험도 중		요청마다 데이터베이스 연결을 열고 닫지 않습니다. 요청이 쌓이면 연결과 파일 핸들이 바닥납니다.
20신뢰할 수 없는 데이터의 역직렬화
(코드오류)		make_token, read_token
위험도 상		토큰을 서명 없는 pickle로 만들고 그대로 pickle.loads합니다. 토큰을 만들어 관리자로 행세할 수 있고, 서버에서 원하는 코드를 실행할 수도 있습니다.
21시스템 데이터 정보노출(응답의 내부 필드)
(캡슐화)		signup
위험도 중		가입 응답에 password_hash와 role을 포함한 행 전체를 담습니다.
22잘못된 세션에 의한 데이터 정보노출
(캡슐화)		read_token, me
위험도 중		로그인한 사용자를 전역 딕셔너리 CURRENT_USER에 담습니다. 동시에 들어온 요청이 서로의 값을 덮어, 다른 사람의 정보가 응답됩니다.
23제거되지 않고 남은 디버그 코드
(캡슐화)		login의 print, debug_config
위험도 상		로그인할 때 비밀번호를 출력해 로그에 남깁니다. /debug/config는 인증 없이 비밀 키와 환경 변수 전체를 보여 줍니다.
24취약한 API 사용
(API 오용)		import_notices
위험도 상		yaml.load(..., Loader=yaml.Loader)는 YAML의 태그로 Python 함수를 실행합니다.
25취약한 외부 패키지 사용
(API 오용)		requirements.txt(requests 2.31.0)
위험도 중		pip-audit이 requests 2.31.0의 알려진 취약점을 보고합니다.

항목 이름에 대해

21번 "시스템 데이터 정보노출"은 이전 판 가이드의 캡슐화 항목 이름입니다. 2021년판에는 같은 이름의 항목이 없지만, 응답에 내부 필드가 섞여 나가는 문제는 여전히 진단 대상입니다. OWASP API Security Top 10의 API3(객체 속성 수준 인가 취약)에 해당합니다. 25번 취약한 외부 패키지는 가이드의 항목이 아니라 이 과정에서 API 오용과 함께 다루는 점검 항목입니다.
