모델, 스키마, 마이그레이션

명세의 자원 표를 SQLAlchemy 모델과 Pydantic 스키마로 옮기고, 첫 마이그레이션 리비전을 만들어 적용합니다.

실습 목표모델과 스키마를 작성하고, 첫 리비전을 만들어 SQLite와 PostgreSQL에 적용할 수 있습니다.

  1. 모델 작성

    app/models.py의 TODO 자리에 주 자원 모델을 넣고, 맨 위의 import를 늘립니다. 예시의 모델은 다음과 같습니다.

    app/models.py의 import
    from sqlalchemy import ForeignKey, String, UniqueConstraint, func, text
from sqlalchemy.orm import Mapped, mapped_column, relationship
    app/models.py에 추가
    class Study(Base):
    """스터디 모임"""

    __tablename__ = "studies"

    id: Mapped[int] = mapped_column(primary_key=True)
    title: Mapped[str] = mapped_column(String(100))
    description: Mapped[str] = mapped_column(String(1000), default="")
    capacity: Mapped[int]  # 정원(개설자 포함)
    member_count: Mapped[int] = mapped_column(default=1, server_default="1")  # 지금 참가 인원(개설자 포함)
    is_open: Mapped[bool] = mapped_column(default=True, server_default=text("true"))  # 모집 중이면 True
    owner_id: Mapped[int] = mapped_column(ForeignKey("users.id"))  # 개설자
    created_at: Mapped[datetime] = mapped_column(server_default=func.now())

    # 이 모임의 참가 기록. 모임을 지우면 참가 기록도 함께 지웁니다.
    memberships: Mapped[list["Membership"]] = relationship(back_populates="study", cascade="all, delete-orphan")


class Membership(Base):
    """누가 어떤 모임에 참가했는지 기록합니다."""

    __tablename__ = "memberships"
    # 한 사람은 한 모임에 한 번만 참가할 수 있게 데이터베이스가 막습니다.
    __table_args__ = (UniqueConstraint("study_id", "user_id", name="uq_memberships_study_user"),)

    id: Mapped[int] = mapped_column(primary_key=True)
    study_id: Mapped[int] = mapped_column(ForeignKey("studies.id"))
    user_id: Mapped[int] = mapped_column(ForeignKey("users.id"))
    joined_at: Mapped[datetime] = mapped_column(server_default=func.now())

    study: Mapped["Study"] = relationship(back_populates="memberships")
    user: Mapped["User"] = relationship()
    설계 선택이유
    member_count를 열로 저장참가할 때마다 참가 기록 수를 세지 않고, 조건부 UPDATE 한 번으로 정원을 검사하려고(S17-P60-01)
    UniqueConstraint("study_id", "user_id")같은 사람이 같은 모임에 두 번 참가하는 것을 코드 검사와 별개로 데이터베이스가 막게 하려고
    cascade="all, delete-orphan"모임을 지우면 그 모임의 참가 기록도 함께 지우려고. 없으면 외래 키 때문에 삭제가 실패합니다.
    owner_id는 필수개설자 없는 모임은 권한 검사를 할 수 없습니다. 값은 요청이 아니라 로그인한 사용자에서 채웁니다.

  2. 스키마 작성

    app/schemas.py의 TODO 자리에 입력 모델과 응답 모델을 넣습니다. 파일 맨 위에 from datetime import datetime도 더합니다. 입력 모델은 반드시 InputModel을 상속합니다.

    app/schemas.py에 추가
    class StudyCreate(InputModel):
    """모임 등록 입력 모델"""
    title: str = Field(min_length=1, max_length=100, examples=["FastAPI 주말 스터디"])
    description: str = Field(default="", max_length=1000, examples=["토요일 오전에 교안을 함께 읽습니다."])
    capacity: int = Field(ge=2, le=50, examples=[6])


class StudyUpdate(InputModel):
    """모임 일부 수정 입력 모델. 모든 항목이 선택입니다."""
    title: str | None = Field(default=None, min_length=1, max_length=100)
    description: str | None = Field(default=None, max_length=1000)
    capacity: int | None = Field(default=None, ge=2, le=50)
    is_open: bool | None = None  # False로 바꾸면 모집을 마감합니다.


class StudyRead(BaseModel):
    """모임 응답 모델"""

    model_config = ConfigDict(from_attributes=True)

    id: int
    title: str
    description: str
    capacity: int
    member_count: int
    is_open: bool
    owner_id: int
    created_at: datetime


class StudyPage(BaseModel):
    """모임 목록 응답. 현재 페이지의 모임과 전체 개수를 함께 돌려줍니다."""
    items: list[StudyRead]
    total: int
    page: int
    size: int


class MemberRead(BaseModel):
    """참가자 명단의 한 줄. 이메일은 일부만 보여 줍니다."""

    model_config = ConfigDict(from_attributes=True)

    user_id: int
    email: str
    joined_at: datetime

    @field_serializer("email")
    def mask_email_field(self, email: str) -> str:
        return mask_email(email)

    등록 모델(StudyCreate)에는 owner_id, member_count, is_open이 없습니다. 이 값들은 서버가 정합니다. 수정 모델(StudyUpdate)은 모든 항목이 선택이고, 규칙은 등록과 같게 맞춥니다. 수정에서 검증 규칙을 빠뜨리면 등록에서 막은 값을 수정으로 넣을 수 있습니다.

    템플릿에는 리비전이 없으므로, 첫 리비전에 회원 관련 테이블과 내 테이블이 함께 들어갑니다. 만들어진 파일을 열어 내 테이블과 유일 제약이 있는지 눈으로 확인합니다. alembic check는 모델과 데이터베이스 사이에 차이가 남아 있지 않은지 확인하는 명령입니다.

  4. PostgreSQL에서도 적용해 보기

    내 PC에서는 SQLite로 리비전을 만들었지만, 운영(RDS)은 PostgreSQL입니다. 두 데이터베이스는 문법이 조금씩 달라서, SQLite에서 만든 리비전이 PostgreSQL에서 실패할 수 있습니다. 배포하는 날 알게 되면 곤란하므로 지금 Compose로 확인합니다. .env의 POSTGRES_PASSWORD를 채운 뒤 실행합니다.

    docker compose up -d --build
docker compose run --rm api alembic upgrade head
INFO  [alembic.runtime.migration] Running upgrade  -> 0a9c91c8786c, create tables
curl -s localhost:8000/health
{"status":"ok","database":"ok"}

    실제로 겪은 차이: 불리언 기본값

    예시를 만들 때 처음에는 is_open의 서버 기본값을 server_default=true()로 적었습니다. SQLite에서 만든 리비전에는 이 값이 sa.text('1')로 기록되었고, PostgreSQL에 적용하자 "boolean 열의 기본값이 integer"라는 오류로 실패했습니다. server_default=text("true")로 바꾸면 두 데이터베이스에서 모두 동작합니다. 리비전을 고쳤으면 SQLite 파일(app.db)과 리비전 파일을 지우고 다시 만듭니다. 아직 아무도 쓰지 않은 첫 리비전이라 다시 만들어도 됩니다.
