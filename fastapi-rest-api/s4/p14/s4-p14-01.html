왜 마이그레이션인가

이 파트의 학습 목표Alembic으로 스키마 변경 이력을 만들고 적용할 수 있습니다.

앞 파트에서 테이블 구조를 바꾸려고 데이터베이스 파일을 지웠습니다. 개발 중에는 괜찮지만 실제 서비스라면 사고입니다. 데이터를 지키면서 테이블 구조를 바꾸는 방법이 마이그레이션입니다.

상황create_all

기존 테이블에 열 추가하지 못함

바뀐 내용을 기록하고 되돌리기하지 못함

스키마 버전 관리

테이블 구조를 스키마라고 합니다. 마이그레이션 도구는 Git이 코드 변경을 기록하듯 스키마 변경을 기록합니다. 변경 하나하나를 리비전이라는 파일로 남기고, 파일마다 "적용하는 방법(upgrade)"과 "되돌리는 방법(downgrade)"이 들어 있습니다.

데이터베이스 안에는 alembic_version이라는 작은 테이블이 생겨 "지금 몇 번 리비전까지 적용되었는지"를 기억합니다. 그래서 개발자 PC, 테스트 서버, 운영 서버가 각자 어디까지 적용되었든 같은 명령(alembic upgrade head)으로 최신 상태를 맞출 수 있습니다. 7일차 AWS 배포에서도 이 명령을 그대로 씁니다.

이 과정에서는 SQLAlchemy를 만든 팀이 만든 마이그레이션 도구인 Alembic을 씁니다.

마이그레이션 작업의 순서

테이블 구조를 바꿀 때는 항상 같은 순서를 따릅니다. 다음 페이지부터 이 순서를 그대로 실습합니다.

순서하는 일명령 또는 파일
1모델을 고칩니다.app/models.py
2모델과 데이터베이스의 차이로 리비전을 만듭니다.alembic revision --autogenerate -m "설명"
3만들어진 리비전 파일을 열어 의도와 같은지 검토합니다.migrations/versions/
4데이터베이스에 적용합니다.alembic upgrade head
5모델과 리비전 파일을 함께 커밋합니다.git add, git commit

데이터베이스가 기억하는 버전

적용을 마친 데이터베이스에서 alembic_version 테이블을 열어 보면 값이 하나 들어 있습니다.

python -c "import sqlite3; print(sqlite3.connect('books.db').execute('select * from alembic_version').fetchall())"
[('10c68672ec78',)]

이 값은 마지막으로 적용한 리비전 파일의 Revision ID와 같습니다(값은 사람마다 다릅니다). alembic upgrade head는 이 값 다음의 리비전만 골라 적용하므로, 같은 명령을 여러 번 실행해도 이미 적용한 변경을 다시 하지 않습니다. 이 테이블을 손으로 고치거나 지우면 Alembic이 현재 상태를 잘못 알게 되므로 건드리지 않습니다.
