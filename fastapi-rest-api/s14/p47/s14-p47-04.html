비밀정보 교체 절차

비밀 값은 새었을 때만이 아니라, 담당자가 바뀌거나 일정 기간이 지났을 때도 바꿉니다. 바꾸는 순서를 미리 정해 두면 서비스를 멈추지 않고 안전하게 바꿀 수 있습니다.

JWT 비밀 키 교체

순서할 일명령이나 방법
1새 값 만들기secrets.token_urlsafe(32)
2Parameter Store 값 덮어쓰기콘솔에서 파라미터를 열고 편집. 버전이 1 올라갑니다.
3앱 다시 시작값은 시작할 때만 읽으므로 컨테이너를 다시 만듭니다(docker compose up -d --force-recreate).
4확인/health, 로그인, 이전 토큰이 401인지

비밀 키를 바꾸면 그 키로 서명한 액세스 토큰은 모두 무효가 됩니다. 사용자 입장에서는 로그인이 풀린 것처럼 보이지만, 도서 API의 리프레시 토큰은 비밀 키로 서명한 값이 아니라 데이터베이스에 해시로 저장한 무작위 값이므로(S5-P18) 앱이 /auth/refresh로 새 액세스 토큰을 받아 이어 쓸 수 있습니다. 실습 환경에서 교체를 재현하면 다음과 같습니다.

시점이전에 받은 액세스 토큰으로 /auth/me
값을 덮어쓴 직후(재시작 전)200(앱은 아직 이전 값을 씀)
컨테이너를 다시 만든 뒤401
다시 로그인해 받은 토큰200

DB 암호 교체

DB 암호는 RDS와 Parameter Store 두 곳에 있어서 순서가 중요합니다. RDS의 암호를 먼저 바꾸면, 앱을 다시 시작하기 전까지 새로 맺는 연결이 실패합니다. 실습 규모에서는 아래 순서로 짧은 중단을 받아들이고, 중단이 없어야 하는 서비스는 DB 계정을 두 개 두고 번갈아 바꾸거나 Secrets Manager의 자동 교체를 씁니다.

순서할 일
1새 암호 만들기
2RDS 콘솔에서 수정, 새 마스터 암호 입력, 즉시 적용
3Parameter Store의 /book-api/DATABASE_URL 값에서 암호 부분만 바꾸기
4앱 다시 시작, /health의 database가 ok인지 확인

노출 사고가 났을 때

순서할 일
1새어 나간 값을 바로 교체합니다. 원인 조사보다 먼저입니다.
2어디로 새었는지(채팅, Git, 로그, 화면 공유) 찾아 지우고, Git 기록이라면 저장소 관리자와 함께 정리합니다.
3CloudTrail에서 그 파라미터를 누가 읽었는지(GetParameter, GetParameters) 확인합니다.
4DB 암호였다면 그 사이 DB에 낯선 접속이나 변경이 없었는지 봅니다. JWT 키였다면 그 사이 발급된 토큰을 믿을 수 없으므로 리프레시 토큰도 모두 폐기하는 것을 검토합니다.

Parameter Store는 값을 바꿀 때마다 버전을 남기므로, 잘못 바꿨을 때 이전 값을 찾아 되돌릴 수 있습니다. 기록은 aws ssm get-parameter-history --name /book-api/SECRET_KEY로 볼 수 있습니다(값은 암호화된 채로 보입니다).

Parameter Store의 SECRET_KEY 값을 바꿨는데 이전 토큰이 계속 통과합니다. 왜 그런가요?
