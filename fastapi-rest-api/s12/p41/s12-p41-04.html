액세스 키 관리 수칙

액세스 키는 AWS를 프로그램으로 다룰 때 쓰는 비밀 값입니다. 편리하지만 가장 자주 새는 비밀 값이기도 합니다. 이 과정에서 액세스 키를 만들지 않는 이유와, 혹시 새었을 때 할 일을 정리합니다.

역할 자격 증명과 SSRF

EC2 서버는 역할의 임시 자격 증명을 인스턴스 메타데이터 서비스(IMDS)에서 받습니다. 서버 안에서만 열리는 주소 169.254.169.254로 요청하면 자격 증명을 돌려줍니다. S11의 진단 실습에서 링크 미리 보기 기능이 이 주소로 요청할 수 있었던 것을 기억하나요? SSRF 약점이 있는 서버는 공격자 대신 이 주소에 요청해 역할의 자격 증명을 넘겨줄 수 있습니다.

이를 막는 장치가 IMDSv2입니다. IMDSv2는 먼저 PUT 요청으로 토큰을 받아야 자격 증명을 주므로, 단순히 URL만 바꿔 GET 요청을 보내게 하는 SSRF로는 꺼내기 어렵습니다. 7일차에 쓸 Amazon Linux 2023은 기본으로 IMDSv2만 허용합니다. 그래도 근본 대책은 애플리케이션에서 SSRF를 막고(S9-P31), 역할에 최소 권한만 주는 것입니다.

키가 새었을 때

순서할 일
1IAM에서 그 액세스 키를 바로 비활성화하고 삭제합니다. 코드에서 지우는 것보다 먼저입니다. Git 기록에는 남아 있기 때문입니다.
2강사(실무에서는 보안 담당)에게 바로 알립니다.
3CloudTrail(AWS 작업 기록)에서 그 키로 무슨 일을 했는지 확인하고, 모르는 자원(특히 다른 리전의 EC2)이 생겼는지 봅니다.
4필요하면 새 키를 만들되, 역할이나 임시 자격 증명으로 바꿀 수 있는지 먼저 검토합니다.

GitHub의 비밀 값 검사

GitHub는 저장소에 올라온 AWS 키 같은 비밀 값을 검사하고, 푸시 단계에서 막거나(푸시 보호) AWS에 알려 줍니다. AWS는 알림을 받으면 키가 노출되었다고 메일을 보내고 위험한 동작을 막는 정책을 자동으로 붙이기도 합니다. 하지만 이는 마지막 안전망일 뿐이므로, 키를 만들지 않는 것이 가장 좋습니다.
