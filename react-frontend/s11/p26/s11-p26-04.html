컨테이너로 통합 실행하고 점검하기

  1. .env.production, nginx/default.conf, nginx/security-headers.conf, Dockerfile, .dockerignore를 작성합니다.
  2. 백엔드의 compose.yaml에 web 서비스를 추가하고 docker compose up -d --build로 실행합니다.
  3. 다음 명령으로 응답을 확인합니다.
# 보안 헤더와 SPA 대체 응답: 없는 파일 경로도 index.html(200)이 와야 합니다.
curl -I http://localhost:8080/books/3

# 프록시: /api/health가 백엔드의 /health로 전달되어야 합니다.
curl http://localhost:8080/api/health

# 해시 파일 캐시: Cache-Control에 immutable이 있어야 합니다.
curl -I http://localhost:8080/assets/$(docker compose exec web ls /usr/share/nginx/html/assets | grep -m1 '\.js$')
  1. 브라우저에서 확인합니다.
번호 확인 내용 기대 결과
1 http://localhost:8080 접속 후 로그인, 목록, 상세, 대여 개발 환경과 같은 동작
2 Network 탭에서 API 요청 주소 http://localhost:8080/api/..., OPTIONS 사전 요청 없음
3 상세 화면에서 새로고침 404 없이 같은 화면
4 표지 이미지 주소 /api/covers/...로 표시
5 관리자로 대시보드 접속 Network 탭에서 DashboardPage-...js가 이때 처음 내려받아짐
6 응답 헤더 content-security-policy, x-frame-options 등 S9의 헤더 존재, Server 헤더에 버전 없음
  1. CSP가 인라인 코드를 막는지 확인합니다. Console에서 다음을 실행합니다.
document.body.insertAdjacentHTML('beforeend', '<img src="x" onerror="console.log(\'실행됨\')">');

개발 서버(localhost:5173)에서는 "실행됨"이 출력되지만, localhost:8080에서는 출력되지 않고 CSP 위반 메시지가 나타납니다. S9의 XSS 실습에서 본 공격 코드가 운영 환경에서는 실행되지 않는다는 뜻입니다.

  1. 이미지 크기를 확인합니다. Node.js가 빠진 최종 이미지는 수십 MB 수준입니다.
docker image ls | grep web
  1. 문제가 생기면 다음을 확인합니다.
증상 확인할 것
/api/... 요청이 502 Bad Gateway api 컨테이너가 실행 중인지 확인합니다. api를 다시 만든 뒤라면 Nginx가 예전 주소를 기억하고 있을 수 있으므로 docker compose restart web
/api/... 요청이 백엔드에서 404 proxy_pass 주소 끝의 / 누락
새로고침하면 Nginx 404 try_files ... /index.html 누락
화면은 뜨는데 API 주소가 127.0.0.1:8000 .env.production 누락 또는 빌드 인자 확인 후 --build로 다시 빌드
보안 헤더가 일부 경로에만 없음 해당 location에 include 누락 (add_header 상속 규칙)
표지 업로드가 413 (Nginx 오류 페이지) client_max_body_size 값
