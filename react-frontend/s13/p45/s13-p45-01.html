실시간 갱신 방식

파트 목표폴링을 올바르게 구현하는 규칙을 설명하고, 브라우저 요청 기록과 지표 계산 함수를 만들어 테스트할 수 있습니다.

방식 원리 장점 단점
폴링 일정 간격으로 요청 구현이 단순하고 기존 REST API 그대로 사용 변화가 없어도 요청, 간격만큼 늦음
SSE(Server-Sent Events) 서버가 열린 연결로 이벤트를 계속 보냄 서버에서 브라우저로의 실시간 전송에 적합 백엔드에 스트리밍 엔드포인트 필요
WebSocket 양방향 연결 유지 양방향 실시간 통신 구현과 운영(프록시, 재연결)이 복잡

백엔드에 실시간 전송 기능이 없으므로 이 과정은 폴링을 사용합니다. 폴링을 올바르게 구현하려면 다음을 지켜야 합니다.

  • 앞의 요청이 끝난 뒤 다음 요청을 예약합니다. setInterval은 응답이 늦어도 정해진 간격마다 요청을 쌓으므로 setTimeout을 이어 붙이는 방식을 씁니다.
  • 탭이 보이지 않을 때(document.visibilityState가 hidden)는 요청을 쉬어 서버 부담을 줄입니다.
  • 화면을 떠나면 타이머를 멈추고 진행 중인 요청을 취소합니다.
  • 간격은 데이터의 성격에 맞춥니다. 헬스 체크는 10초, 업무 지표는 60초처럼 차등을 둡니다.

이 과정은 이 규칙을 직접 구현하지 않고 S10에서 도입한 TanStack Query의 refetchInterval로 해결합니다. refetchInterval은 앞 요청이 끝나기 전에 다음 요청을 겹쳐 보내지 않고, 탭이 보이지 않으면 쉬며(refetchIntervalInBackground의 기본값 false), 화면을 떠나면 멈춥니다. 위 규칙을 라이브러리가 지켜 주는 것입니다. 규칙 자체를 알아 두어야 라이브러리 없이 구현하거나 다른 도구를 고를 때도 같은 기준으로 판단할 수 있습니다.
