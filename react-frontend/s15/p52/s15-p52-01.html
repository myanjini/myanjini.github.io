Dockerfile 작성

파트 목표멀티 스테이지 빌드로 작고 안전한 프론트엔드 이미지를 만들고, 컨테이너 하나로 실행해 응답을 확인할 수 있습니다.

프로젝트 루트에 Dockerfile을 작성합니다.

Dockerfile
# 1단계: Node.js로 정적 파일을 빌드합니다.
FROM node:24-alpine AS build
WORKDIR /app

# 의존성 목록만 먼저 복사하면 소스가 바뀌어도 설치 단계 캐시를 다시 씁니다.
COPY package.json package-lock.json ./
RUN npm ci

COPY . .
# VITE_ 값은 빌드할 때 코드에 새겨집니다. 실행할 때 바꿀 수 없습니다.
ARG VITE_API_BASE_URL=/api
ENV VITE_API_BASE_URL=${VITE_API_BASE_URL}
RUN npm run build

# 2단계: 빌드 결과물만 Nginx 이미지에 담습니다. Node.js와 소스 코드는 들어가지 않습니다.
# nginx-unprivileged 이미지는 root가 아닌 사용자로 8080 포트에서 실행됩니다.
FROM nginxinc/nginx-unprivileged:stable-alpine
COPY nginx/default.conf /etc/nginx/conf.d/default.conf
COPY nginx/security-headers.conf /etc/nginx/snippets/security-headers.conf
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 8080
HEALTHCHECK --interval=30s --timeout=3s CMD wget -qO- http://127.0.0.1:8080/ > /dev/null || exit 1

멀티 스테이지 빌드. 첫 번째 단계(build)는 Node.js 이미지에서 의존성을 설치하고 빌드합니다. 두 번째 단계는 Nginx 이미지에 빌드 결과물(dist)만 복사합니다. 최종 이미지에는 Node.js, node_modules, 소스 코드가 들어가지 않으므로 크기가 작고, 공격에 쓰일 수 있는 도구와 정보도 줄어듭니다. 백엔드 과정 S8-P26에서 만든 API 이미지와 같은 원리입니다.

캐시를 고려한 순서. package.json과 package-lock.json만 먼저 복사해 npm ci를 실행하고, 그 다음에 소스 전체를 복사합니다. Docker는 단계별로 결과를 캐시하므로, 소스만 바뀌고 의존성 목록이 그대로면 시간이 오래 걸리는 설치 단계를 건너뜁니다.

npm ci. npm install과 달리 package-lock.json에 적힌 버전 그대로 설치하고, 잠금 파일과 package.json이 맞지 않으면 실패합니다. 언제 빌드해도 같은 의존성이 들어가므로 S12-P42-01의 공급망 관리 원칙에 맞습니다.

빌드 인자. ARG VITE_API_BASE_URL=/api와 ENV로 빌드 시점에 값을 넘길 수 있게 했습니다. 환경 변수로 넘긴 값은 .env.production보다 우선합니다. 다른 주소로 빌드해야 할 때는 docker build --build-arg VITE_API_BASE_URL=... .를 씁니다.

root가 아닌 사용자로 실행. nginxinc/nginx-unprivileged 이미지는 Nginx를 root가 아닌 사용자로 실행하며, 이 때문에 1024 미만 포트 대신 8080 포트를 사용합니다. 컨테이너 안의 프로세스가 탈취되더라도 피해 범위를 줄일 수 있습니다.

헬스 체크. HEALTHCHECK로 Docker가 30초마다 Nginx의 응답을 확인하고, docker compose ps에 healthy 여부를 표시합니다.

이미지에 넣지 않을 파일은 .dockerignore에 적습니다. 특히 node_modules를 제외하지 않으면 운영체제가 다른 로컬의 모듈이 이미지로 복사되어 빌드가 느려지거나 오동작할 수 있습니다. .env.local처럼 개인 설정 파일도 제외합니다.
