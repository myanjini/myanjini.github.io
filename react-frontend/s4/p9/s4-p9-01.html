CORS

동일 출처 정책은 안전하지만, 이 과정처럼 프론트엔드와 백엔드가 다른 출처에서 동작하는 정상적인 경우까지 막아 버립니다. CORS(Cross-Origin Resource Sharing, 교차 출처 자원 공유)는 서버가 응답 헤더로 "이 출처는 내 응답을 읽어도 된다"고 허락하는 방법입니다. 허락의 주체는 서버이고, 허락을 확인하고 집행하는 주체는 브라우저입니다.

단순 요청

다음 조건을 모두 만족하는 요청은 단순 요청(simple request)으로 취급되어 바로 전송됩니다.

  • 메서드가 GET, HEAD, POST 중 하나입니다.
  • 직접 지정한 헤더가 Accept, Accept-Language, Content-Language, Content-Type 같은 안전 목록 헤더뿐입니다. Authorization 헤더가 있으면 단순 요청이 아닙니다.
  • Content-Type이 application/x-www-form-urlencoded, multipart/form-data, text/plain 중 하나입니다. application/json이면 단순 요청이 아닙니다.

단순 요청의 흐름은 다음과 같습니다.

브라우저                                            서버(127.0.0.1:8000)
   │ GET /books?limit=3                                │
   │ Origin: http://localhost:5173  ─────────────────> │ 요청 처리 (로그에 기록됨)
   │                                                   │
   │ <───────────────────────────────── 200 OK         │
   │     Access-Control-Allow-Origin: http://localhost:5173  (허락한 경우에만 있음)
   │
   └ 브라우저 판단: 허락 헤더가 내 출처와 일치하면 JavaScript에 응답 전달, 없으면 차단

브라우저는 교차 출처 요청에 Origin 헤더를 자동으로 붙입니다. 서버가 응답에 Access-Control-Allow-Origin 헤더를 넣어 그 출처를 허락하면 JavaScript가 응답을 읽을 수 있고, 헤더가 없으면 S4-P8-01처럼 차단됩니다.

사전 요청(preflight)

단순 요청이 아닌 요청은 본 요청을 보내기 전에 OPTIONS 메서드로 "이런 요청을 보내도 되는가"를 먼저 묻습니다. 이를 사전 요청이라고 합니다. 서버가 허락하지 않으면 본 요청은 아예 전송되지 않습니다.

브라우저                                            서버
   │ OPTIONS /books                                    │
   │ Origin: http://localhost:5173                     │
   │ Access-Control-Request-Method: POST               │
   │ Access-Control-Request-Headers: authorization,content-type ──> │
   │                                                   │
   │ <──────────────────────────── 200 OK              │
   │   Access-Control-Allow-Origin: http://localhost:5173
   │   Access-Control-Allow-Methods: DELETE, GET, ..., POST
   │   Access-Control-Allow-Headers: authorization,content-type
   │   Access-Control-Max-Age: 600   (이 결과를 600초 동안 재사용)
   │                                                   │
   │ POST /books  (본 요청)                            │
   │ Authorization: Bearer eyJ...                      │
   │ Content-Type: application/json  ────────────────> │

이 과정에서 호출하는 API가 각각 어떤 요청에 해당하는지 정리하면 다음과 같습니다.

요청 종류 이유
GET /books 단순 요청 GET, 특별한 헤더 없음
POST /auth/token (로그인) 단순 요청 POST, 폼 형식, Authorization 없음
GET /auth/me 사전 요청 Authorization 헤더
POST /books 사전 요청 application/json, Authorization
POST /books/{id}/cover 사전 요청 Authorization (멀티파트 자체는 단순 형식)
DELETE /books/{id} 사전 요청 DELETE 메서드

로그인 요청이 단순 요청이라는 점에 주목합니다. 허락하지 않은 출처에서 보낸 로그인 요청도 서버까지는 도달해 처리된다는 뜻입니다. 백엔드 과정 S10-P34에서 로그인 실패 횟수를 서버에서 제한한 이유 중 하나입니다.

응답 헤더 노출

CORS가 허락된 응답이라도 JavaScript가 읽을 수 있는 응답 헤더는 기본적으로 Cache-Control, Content-Language, Content-Length, Content-Type, Expires, Last-Modified, Pragma 일곱 가지뿐입니다. 백엔드가 보내는 Retry-After(로그인 잠금 시간), X-Request-ID, X-Process-Time(S8-P28)을 프론트엔드에서 읽으려면 서버가 Access-Control-Expose-Headers로 명시해야 합니다.

자격 증명이 포함된 요청

브라우저는 교차 출처 요청에 쿠키를 기본적으로 보내지 않습니다. 쿠키를 보내려면 프론트엔드에서 fetch(url, { credentials: 'include' })나 axios의 withCredentials: true를 지정하고, 서버는 Access-Control-Allow-Credentials: true를 보내야 합니다. 이때 Access-Control-Allow-Origin에 와일드카드 *를 쓸 수 없고 정확한 출처를 적어야 합니다. 이 과정의 백엔드는 토큰을 쿠키가 아니라 Authorization 헤더로 주고받으므로 자격 증명 설정이 필요하지 않습니다. 쿠키 방식과의 비교는 S9에서 다룹니다.
