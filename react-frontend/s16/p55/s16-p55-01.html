S3 정적 웹 호스팅

파트 목표S3 정적 웹 호스팅으로 프론트엔드를 배포하고, 다른 출처가 되는 API와의 CORS 설정을 맞출 수 있으며, CloudFront를 쓰는 이유를 설명할 수 있습니다.

빌드 결과물은 HTML, JavaScript, CSS 파일일 뿐이므로 파일을 그대로 내려주는 저장소만 있으면 서비스할 수 있습니다. Amazon S3는 버킷에 파일을 저장하는 객체 저장소이며, 버킷에 정적 웹 사이트 호스팅을 켜면 웹 서버처럼 동작하는 주소가 생깁니다. 서버를 직접 운영하지 않으므로 관리할 것이 적고, 저장한 용량과 전송량만큼만 비용을 냅니다.

항목 내용
웹사이트 주소 http://<버킷>.s3-website.<리전>.amazonaws.com (HTTP만 지원)
인덱스 문서 폴더 주소를 요청했을 때 돌려줄 파일. index.html
오류 문서 없는 파일을 요청했을 때 돌려줄 파일. SPA는 index.html로 지정해 대체 응답을 흉내 냄 (상태 코드는 404)
공개 설정 버킷의 퍼블릭 액세스 차단을 끄고, 누구나 s3:GetObject를 할 수 있는 버킷 정책 추가
응답 헤더 파일별 Cache-Control, Content-Type만 지정 가능. CSP 같은 보안 헤더는 넣을 수 없음

S15의 Nginx 구성과 가장 크게 다른 점은 출처입니다. S3는 /api/를 백엔드로 넘겨 주는 프록시가 없으므로, 화면은 S3 주소에서, API는 백엔드 과정 S13~S15에서 배포한 백엔드의 공개 주소에서 받습니다. 두 주소는 다른 출처이므로 S5에서 배운 CORS가 다시 필요합니다.

  • 빌드할 때 VITE_API_BASE_URL에 백엔드의 공개 주소를 절대 주소로 넣습니다(S15-P50-02의 6번).
  • 백엔드의 CORS_ORIGINS에 S3 웹사이트 주소를 등록합니다. 주소 끝에 /를 붙이지 않고 스킴부터 정확히 적습니다.
  • 백엔드가 표지 파일을 S3에 저장하도록 바꿨다면(백엔드 S15-P50) 표지 주소가 https://...로 시작하는 완전한 주소로 옵니다. toAssetUrl은 이 경우 API 주소를 붙이지 않아야 합니다.
