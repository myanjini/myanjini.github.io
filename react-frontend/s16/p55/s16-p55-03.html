S3 버킷 만들고 수동 배포하기

AWS CLI가 설치되어 있고 aws configure로 내 계정의 자격 증명이 설정되어 있다고 가정합니다. 리전은 ap-northeast-2(서울)를 씁니다. 버킷 이름은 전 세계에서 하나뿐이어야 하므로 react-frontend-<내 이름>-<숫자>처럼 정합니다.

1) 버킷 만들기와 웹 호스팅 켜기

export BUCKET=react-frontend-hong-1234
export AWS_REGION=ap-northeast-2

aws s3 mb "s3://$BUCKET" --region "$AWS_REGION"
aws s3 website "s3://$BUCKET" --index-document index.html --error-document index.html

2) 공개 읽기 허용

새 버킷은 퍼블릭 액세스 차단이 켜져 있어 공개 정책을 붙일 수 없습니다. 차단을 끄고, 파일 읽기만 허용하는 정책을 붙입니다. 정책 파일의 BUCKET_NAME을 내 버킷 이름으로 바꿉니다.

deploy/s3-bucket-policy.json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "PublicReadForStaticWebsite",
      "Effect": "Allow",
      "Principal": "*",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::BUCKET_NAME/*"
    }
  ]
}
aws s3api put-public-access-block --bucket "$BUCKET" \
  --public-access-block-configuration BlockPublicAcls=false,IgnorePublicAcls=false,BlockPublicPolicy=false,RestrictPublicBuckets=false
sed "s/BUCKET_NAME/$BUCKET/" deploy/s3-bucket-policy.json > /tmp/policy.json
aws s3api put-bucket-policy --bucket "$BUCKET" --policy file:///tmp/policy.json

정책은 s3:GetObject(파일 읽기)만 허용합니다. 목록 보기나 쓰기는 허용하지 않습니다.

3) 표지 주소 처리 보완

toAssetUrl이 완전한 주소는 그대로 쓰도록 한 줄을 추가하고 테스트로 지킵니다.

export function toAssetUrl(path) {
  if (!path) return null;
  if (/^https?:\/\//.test(path)) return path;
  return `${API_BASE_URL}${path}`;
}
src/api/client.test.js
import { describe, expect, it } from 'vitest';
import { toAssetUrl } from './client';

describe('toAssetUrl', () => {
  it('경로에는 API 주소를 붙인다', () => {
    expect(toAssetUrl('/covers/a.png')).toBe('http://api.test/covers/a.png');
  });

  it('완전한 주소는 그대로 둔다', () => {
    const url = 'https://bucket.s3.ap-northeast-2.amazonaws.com/covers/a.png';
    expect(toAssetUrl(url)).toBe(url);
  });

  it('값이 없으면 null을 돌려준다', () => {
    expect(toAssetUrl(null)).toBeNull();
  });
});

4) 빌드와 업로드

백엔드의 공개 주소로 빌드해 올립니다. 해시가 붙은 파일과 index.html의 캐시 설정을 나눠 두 번 올립니다. S15-P51에서 Nginx에 적용한 캐시 규칙과 같습니다.

VITE_API_BASE_URL=https://<백엔드 공개 주소> npm run build

aws s3 sync dist/assets "s3://$BUCKET/assets" --delete \
  --cache-control "public, max-age=31536000, immutable"
aws s3 sync dist "s3://$BUCKET" --delete --exclude "assets/*" --cache-control "no-cache"

5) 백엔드 CORS 등록과 확인

백엔드 서버의 환경 변수 CORS_ORIGINS에 http://<버킷>.s3-website.ap-northeast-2.amazonaws.com을 추가하고 백엔드를 다시 시작합니다. 그리고 다음을 확인합니다.

  1. 웹사이트 주소로 접속해 목록, 로그인, 상세가 동작합니다.
  2. Network 탭에서 API 요청이 백엔드 공개 주소로 나가고, 로그인 후 요청에 OPTIONS 사전 요청이 보입니다. S15의 같은 출처 구성과 다른 점입니다.
  3. /books/3에서 새로고침하면 화면은 정상이지만, Network 탭의 문서 요청 상태가 404입니다. 오류 문서로 대체 응답을 흉내 냈기 때문입니다.
  4. curl -I로 웹사이트 주소의 응답 헤더를 보면 content-security-policy가 없습니다. CloudFront가 필요한 이유 중 하나입니다.
  5. 백엔드 CORS_ORIGINS에서 S3 주소를 잠시 빼면 Console에 CORS 오류가 나고 화면에 "서버에 연결할 수 없습니다."가 표시되는지 확인하고 되돌립니다.
