보안 점검하기

1) XSS 동작 확인

임시 컴포넌트를 만들어 이스케이프와 dangerouslySetInnerHTML의 차이를 확인합니다. 확인이 끝나면 반드시 지웁니다. 아래 문자열은 이미지 로딩 오류 시 같은 출처의 sessionStorage를 읽어 출력하는 코드로, XSS가 토큰을 읽을 수 있음을 보여 줍니다.

// src/pages/XssLab.jsx (실습 후 삭제)
const payload = `<img src="x" onerror="console.log('읽힘:', sessionStorage.getItem('book-admin.refresh'))">`;

export default function XssLab() {
  return (
    <section>
      <h2>1. JSX 출력 (안전)</h2>
      <p>{payload}</p>
      <h2>2. dangerouslySetInnerHTML (위험)</h2>
      <div dangerouslySetInnerHTML={{ __html: payload }} />
    </section>
  );
}

App.jsx에 <Route path="xss" element={<XssLab />} />를 잠시 추가하고 로그인한 상태로 /xss를 엽니다. 1번은 글자 그대로 보이고, 2번은 Console에 리프레시 토큰이 출력됩니다. 확인 후 파일과 라우트를 지웁니다. 같은 종류의 인라인 코드가 CSP로 차단되는 모습은 S11에서 Nginx로 보안 헤더를 적용한 뒤 확인합니다.

2) 의존성 점검

npm audit
npm audit --omit=dev
npm audit signatures

발견된 취약점이 있으면 npm audit fix로 호환되는 범위에서 고치고, 메이저 버전 변경이 필요하면 영향 범위를 확인한 뒤 갱신합니다.

3) 빌드 결과물 확인

S5에서 만든 개발용 API 주소를 넣어 빌드한 뒤 결과물을 확인합니다. 운영용 설정 파일(.env.production)은 S11에서 만들므로 여기서는 값을 명령에 직접 넣습니다.

VITE_API_BASE_URL=http://127.0.0.1:8000 npm run build
ls dist/assets                             # .map 파일이 없어야 합니다.
grep -o "127.0.0.1:8000" dist/assets/*.js  # 환경 변수 값이 코드에 새겨진 것을 확인합니다.

API 주소가 빌드 결과물에 문자열로 들어 있는 것을 확인했다면, 비밀정보를 VITE_ 변수에 넣으면 안 되는 이유를 직접 본 것입니다. Windows의 PowerShell에서는 $env:VITE_API_BASE_URL="http://127.0.0.1:8000"; npm run build로 실행합니다.

4) 코드 검색

grep -rn "dangerouslySetInnerHTML\|innerHTML\|eval(\|localStorage" src
grep -rn "console.log" src

결과가 없거나 의도한 곳뿐인지 확인합니다.
