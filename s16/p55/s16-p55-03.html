장애 대응 실습

두 시나리오를 차례로 일으키고, 탐지부터 기록까지 절차대로 대응합니다. 각 단계의 시각을 장애 대응 기록에 적으며 진행합니다.

실습 목표로그와 경보로 장애를 찾고, 이미지 롤백과 설정 복구로 서비스를 되살린 뒤 기록을 남길 수 있습니다.

장애 대응 기록 양식 내려받기(Markdown)

  1. 시작 전 정상 상태 기록

    Windows에서 실행할 때

    아래 명령에는 bash 문법(이름=값, $(...) 등)이 들어 있습니다. 내 PC가 Windows라면 명령 프롬프트가 아니라 Git Bash에서 실행합니다(S12-P40-03). EC2 서버의 접속 화면에서 실행하는 명령은 그대로 입력합니다.

    # EC2
grep IMAGE ~/book-api/.env
IMAGE=123456789012.dkr.ecr.ap-northeast-2.amazonaws.com/book-api:git-9c2e5d1
# 내 PC
aws ssm get-parameter --name /book-api/DATABASE_URL --query Parameter.Version
1
    항목내 값
    정상 이미지 태그
    DATABASE_URL 정상 버전

  2. 시나리오 A: 잘못된 이미지 배포

    내 PC에서 Dockerfile 마지막 줄의 포트를 8080으로 바꿔 main에 푸시합니다. 배포 워크플로가 실행되고, 마지막 확인 단계가 2분쯤 재시도하다 실패합니다. 그 사이 ALB로 접속해 증상을 봅니다.

    git commit -am "Dockerfile 정리(실습용 실수)"
git push

curl -s -o /dev/null -w "%{http_code}\n" $ALB/health
502

    서버에서 상태와 로그를 봅니다. 컨테이너는 떠 있지만 8080에서 기다리고 있습니다.

    docker compose -f compose.prod.yaml ps --format "{{.Image}}  {{.Status}}"
...book-api:git-3f1a7b2  Up 2 minutes (unhealthy)
docker compose -f compose.prod.yaml logs api --tail 3 | grep "Uvicorn running"
{"time": "...", "level": "INFO", "logger": "uvicorn.error", "message": "Uvicorn running on http://0.0.0.0:8080 (Press CTRL+C to quit)", "request_id": "-"}

  3. 시나리오 A: 롤백

    원인을 이미 짐작했더라도, 먼저 직전 정상 이미지로 되돌립니다. 이미지가 ECR에 남아 있으므로 빌드할 필요가 없습니다.

    cd ~/book-api
sed -i 's|^IMAGE=.*|IMAGE=123456789012.dkr.ecr.ap-northeast-2.amazonaws.com/book-api:git-9c2e5d1|' .env
docker compose -f compose.prod.yaml up -d
(30초쯤 뒤)
docker compose -f compose.prod.yaml ps --format "{{.Image}}  {{.Status}}"
...book-api:git-9c2e5d1  Up 35 seconds (healthy)
    curl -s $ALB/health
{"status":"ok","database":"ok"}

    서비스가 돌아왔습니다. 그다음 코드를 고칩니다. 실수한 커밋을 되돌려 푸시하면 정상 코드가 새 커밋 태그로 다시 배포됩니다.

    git revert --no-edit HEAD
git push

  4. 시나리오 B: DB 연결 오류 일으키기

    콘솔의 Parameter Store에서 /book-api/DATABASE_URL을 편집해 암호 부분의 마지막 글자 세 개를 바꿔 저장합니다(버전 2가 됩니다). 서버에서 앱을 다시 시작합니다.

    docker compose -f compose.prod.yaml up -d --force-recreate
curl -s $ALB/health
{"status":"error","database":"unreachable"}

  5. 시나리오 B: 로그로 원인 찾기

    CloudWatch Logs Insights에서 최근 오류를 봅니다. 결과 한 줄을 펼치면 error 필드에 트레이스백이 있고, 마지막 부분에 원인이 있습니다.

    최근 ERROR 로그
    fields @timestamp, request_id, message, path
| filter level = "ERROR"
| sort @timestamp desc
| limit 20
    ... psycopg.OperationalError: connection failed: connection to server at "10.0.11.152", port 5432 failed: FATAL:  password authentication failed for user "bookapi"

    원인은 "암호가 틀림"입니다. 네트워크(보안 그룹)나 RDS 자체의 문제가 아닙니다. 로그에 암호 값은 찍히지 않았다는 것도 확인합니다(S10에서 hide_parameters와 마스킹을 넣은 덕분입니다). 같은 원인의 오류가 언제부터 몇 번 났는지도 셉니다.

    원인별로 시간대 집계
    fields @timestamp, request_id
| filter level = "ERROR" and error like /password authentication failed/
| stats count() as errors by bin(1m)

  6. 시나리오 B: 이전 값으로 복구

    Parameter Store는 이름 뒤에 :버전을 붙여 이전 값을 읽을 수 있습니다. 화면에 값을 찍지 않고 이전 버전 값을 그대로 새 버전으로 저장합니다.

    aws ssm put-parameter --name /book-api/DATABASE_URL --type SecureString --overwrite \
  --value "$(aws ssm get-parameter --name /book-api/DATABASE_URL:1 --with-decryption --query Parameter.Value --output text)"
{
    "Version": 3,
    "Tier": "Standard"
}

    명령 기록에 값이 남지 않나요?

    명령에 적힌 것은 $(...)라는 식이고, 값 자체는 실행할 때만 만들어져 명령 기록에는 남지 않습니다. 다만 같은 PC의 다른 사용자가 실행 중인 프로세스 목록을 보면 잠깐 보일 수 있으므로, 공용 PC에서는 콘솔에서 이전 버전 값을 복사해 붙여 넣는 방법을 씁니다.

    docker compose -f compose.prod.yaml up -d --force-recreate
curl -s $ALB/health
{"status":"ok","database":"ok"}

  7. RDS 백업 확인

    데이터 자체가 잘못된 장애(실수로 테이블을 지움 등)라면 RDS 백업으로 되돌립니다. 이번에는 복원하지 않고, 무엇이 남아 있는지만 확인합니다.

    aws rds describe-db-instances --db-instance-identifier book-api-db --query "DBInstances[0].[BackupRetentionPeriod,LatestRestorableTime]" --output text
1	2026-11-24T06:35:00+00:00

aws rds describe-db-snapshots --db-instance-identifier book-api-db --snapshot-type automated --query "DBSnapshots[].[DBSnapshotIdentifier,SnapshotCreateTime,Encrypted]" --output text
rds:book-api-db-2026-11-23-17-05	2026-11-23T17:05:12+00:00	True

    LatestRestorableTime은 "이 시각까지는 되돌릴 수 있다"는 뜻이고, 보통 몇 분 전입니다. 시점 복원을 하면 기존 DB를 덮어쓰지 않고 새 DB 인스턴스가 만들어지므로, 복원한 뒤 DATABASE_URL의 주소를 새 엔드포인트로 바꿔야 합니다. 복원에는 수십 분이 걸리고 새 인스턴스 요금이 붙으므로 실습에서는 하지 않습니다.
