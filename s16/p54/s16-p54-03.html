내 환경 점검과 조치

부록 C 점검표로 내 배포 환경을 하나씩 확인하고, "아니요"가 나온 항목을 조치합니다. 이 작성본이 8일차 평가 대상입니다.

실습 목표점검표의 항목마다 근거를 들어 확인하고, 과다 권한과 열린 설정을 조치할 수 있습니다.

부록 C 점검표 양식 내려받기(Markdown)

  1. 애플리케이션 항목(1~7)

    번호확인 방법
    1git log -p | grep -c -E "SECRET_KEY=.{20,}"가 0, 서버 .env에 IMAGE와 COVER_BUCKET만, docker inspect에 비밀 값 없음(S14-P49-04)
    2ALB로 /books/abc(잘못된 경로 값)를 요청해 422 본문에 입력 값과 내부 정보가 없는지, X-Request-ID만 있는지
    3curl -o /dev/null -w "%{http_code}" $ALB/docs가 404
    4아래 CORS 확인 명령
    5틀린 비밀번호 6번에 429, 액세스 토큰 만료 15분(설정값)
    6.txt 업로드가 415, S3 퍼블릭 액세스 차단 4개 true
    7최근 배포 실행(Actions)의 bandit, pip-audit 단계가 성공

    Windows에서 실행할 때

    아래 명령에는 bash 문법(이름=값, $(...) 등)이 들어 있습니다. 내 PC가 Windows라면 명령 프롬프트가 아니라 Git Bash에서 실행합니다(S12-P40-03). EC2 서버의 접속 화면에서 실행하는 명령은 그대로 입력합니다.

    ALB=http://book-api-alb-1234567890.ap-northeast-2.elb.amazonaws.com
curl -s -o /dev/null -D - -X OPTIONS $ALB/books -H "Origin: http://evil.example" -H "Access-Control-Request-Method: GET" | grep -i -E "^HTTP|access-control-allow-origin"
HTTP/1.1 400 Bad Request

    도서 API는 아직 브라우저 화면이 없는데, 설정에는 개발용 http://localhost:5173이 그대로 허용되어 있습니다. 4번은 "아니요"입니다. 운영용 Compose의 environment에 아래 줄을 더하고 푸시하면 배포 워크플로가 반영합니다. 위 명령처럼 허용하지 않은 Origin은 Access-Control-Allow-Origin 헤더 없이 거부되어야 합니다.

    compose.prod.yaml의 environment에 추가
          CORS_ORIGINS: "[]"  # 브라우저 화면이 없으므로 어떤 Origin도 허용하지 않습니다. 화면이 생기면 그 주소만 적습니다.

  2. AWS 항목(8~14)

    # 8. 내 사용자의 MFA
aws iam list-mfa-devices --query "MFADevices[].SerialNumber"

# 9. EC2 역할의 권한 목록
aws iam list-attached-role-policies --role-name book-api-ec2-role --query "AttachedPolicies[].PolicyName"
aws iam list-role-policies --role-name book-api-ec2-role --query PolicyNames
[
    "book-api-logs",
    "book-api-read-parameters",
    "book-api-s3-covers"
]

# 10. 0.0.0.0/0이 열린 인바운드 규칙 찾기
aws ec2 describe-security-groups --filters Name=vpc-id,Values=vpc-0a1b2c3d4e5f67890 Name=ip-permission.cidr,Values=0.0.0.0/0 --query "SecurityGroups[].[GroupName,IpPermissions[].FromPort]" --output text
book-api-alb-sg	80

# 11. RDS 공개 여부와 암호화
aws rds describe-db-instances --db-instance-identifier book-api-db --query "DBInstances[0].[PubliclyAccessible,StorageEncrypted]" --output text
False	True

# 13. 로그 그룹 보존 기간
aws logs describe-log-groups --log-group-name-prefix /book-api --query "logGroups[].[logGroupName,retentionInDays]" --output text
/book-api/app	30

# 14. Owner 태그가 붙은 내 자원 목록
aws resourcegroupstaggingapi get-resources --tag-filters Key=Owner,Values=student07 --query "ResourceTagMappingList[].ResourceARN" --output text

    10번에서 book-api-alb-sg 말고 다른 보안 그룹이 나오면 "아니요"입니다. 12번은 GitHub 저장소의 Secrets에 AWS 키가 없고, 배포 실행 기록의 자격 증명 단계가 역할(assumed-role/book-api-github-deploy)을 썼는지로 확인합니다. 14번의 태그 목록에서 빠진 자원(예: 대상 그룹, 경보)이 보이면 태그를 붙입니다.

  3. 도구로 한 번 더

    Trusted Advisor 콘솔의 보안에서 새로 고침을 누르고, 빨간색이나 노란색 항목을 확인합니다. IAM의 book-api-ec2-role에서 마지막 액세스 탭을 열어 쓰지 않은 서비스가 있는지 봅니다. ECR에서 지금 배포된 git- 태그 이미지의 스캔 결과에 CRITICAL이나 HIGH가 있으면 판정 근거를 점검표에 적습니다.

  4. 조치하고 다시 확인

    "아니요"인 항목을 고친 뒤 같은 명령으로 다시 확인하고, 점검표의 결과를 "예"로 바꿉니다. 조치하지 못한 항목은 이유와 계획을 적습니다(예: HTTPS는 도메인이 없어 미적용, 시연으로 대체).
