보안 점검

이 파트의 학습 목표프로젝트의 보안약점을 점검하고 기존 배포 파이프라인으로 AWS에 배포할 수 있습니다.

배포하기 전에 내 프로젝트를 스스로 진단합니다. 자동 점검 도구를 먼저 돌리고, 도구가 보지 못하는 부분은 7개 유형의 점검 질문으로 확인합니다. 5일차에 남의 코드(진단용 예제 API)로 연습한 것을 이번에는 내 코드에 합니다.

실습 목표bandit과 pip-audit 결과를 판정하고, 부록 F 진단표로 내 프로젝트를 자기 진단하고 조치할 수 있습니다.

자기 진단표 양식 내려받기(Markdown)

  1. 자동 점검

    bandit -r app -ll
Test results:
	No issues identified.
...
	Total issues (by severity):
		Low: 1
		Medium: 0
		High: 0

pip-audit -r requirements.txt
No known vulnerabilities found

    -ll은 중간 이상만 보여 주는 옵션이라 "찾은 것 없음"으로 나오지만, 요약에는 낮음 1건이 있습니다. 옵션 없이 실행하면 app/routers/auth.py의 "token_type": "bearer"를 "비밀번호를 코드에 적은 것 같다"(B105)고 알려 줍니다. 토큰의 종류를 나타내는 정해진 단어일 뿐 비밀 값이 아니므로 오탐입니다. 진단표의 자동 점검 표에 "낮음 1건, B105 오탐(비밀 값 아님)"처럼 판정과 이유를 적습니다(S11-P37-03).

  2. 유형별 점검

    양식의 "유형별 점검" 표에서 7개 유형마다 내 코드의 해당 위치를 찾아 답합니다. 자동 도구가 찾지 못하는 약점(인가 누락, 경쟁 조건, 응답 속 개인정보)은 대부분 여기서 나옵니다. 오전에 쓴 보안 요구사항(S17-P57-03)과 테스트가 근거가 됩니다.

  3. 진단과 조치 결과 적기

    점검하다 찾은 약점, 그리고 오전에 구현하며 이미 막은 약점을 모두 "진단과 조치 결과" 표에 적습니다. 처음부터 막아 둔 것도 "무엇을 왜 막았는지"를 적어야 평가에서 근거가 됩니다.

  4. 배포 전 점검표의 애플리케이션 항목

    부록 C의 1~7번(S16-P54-03)을 내 프로젝트로 한 번 더 봅니다. 템플릿을 그대로 썼다면 대부분 이미 "예"입니다. 특히 4번(CORS)은 템플릿 기본값이 "허용 없음"이므로 바꾸지 않았는지, 3번(/docs)은 운영에서 꺼지는지(APP_ENV=production) 확인합니다.
