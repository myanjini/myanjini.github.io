보안약점 진단 2

나머지 다섯 유형은 코드의 "모양"보다 "상황"에서 드러나는 것이 많습니다. 동시에 요청이 들어오면, 오류가 나면, 값이 없으면 어떻게 되는지를 떠올리며 읽습니다. 마지막에 자동 점검 도구의 결과를 내 진단과 견주어 봅니다.

실습 목표에러처리, 시간 및 상태, 코드오류, 캡슐화, API 오용 유형을 진단하고, 도구 결과를 진단에 반영할 수 있습니다.

길잡이 질문

유형질문
에러처리처리하지 못한 예외가 나면 응답에 무엇이 담기나요? 없는 공지 번호를 조회해 보세요. 예외를 잡고 아무것도 하지 않는 곳이 있나요?
시간 및 상태값을 읽고, 계산하고, 다시 쓰는 곳이 있나요? 그 사이에 다른 요청이 끼어들면 어떻게 되나요? 끝나지 않을 수 있는 반복문이 있나요?
코드오류조회 결과가 없을 때를 확인하지 않는 곳이 있나요? 연 것(데이터베이스 연결, 파일)을 닫나요? 밖에서 온 데이터를 객체로 되살리는 곳이 있나요?
캡슐화응답에 필요 이상의 필드가 담기나요? 요청 사이에 공유되는 전역 변수가 있나요? 개발할 때 쓰던 코드나 API가 남아 있나요?
API 오용S11-P37-01의 위험한 함수 표에 있는 함수를 쓰나요? 설치하는 패키지에 알려진 취약점이 있나요?
동시 요청으로 확인해 보기

시간 및 상태와 캡슐화의 일부는 동시에 요청을 보내야 드러납니다. 서버를 띄운 채로 다른 터미널에서 Python 대화형 셸을 열어 실행합니다. 공지 번호와 토큰은 자기 것으로 바꿉니다.

Python 셸
from concurrent.futures import ThreadPoolExecutor
import httpx
like = lambda _: httpx.post("http://127.0.0.1:8000/notices/1/like").json()
list(ThreadPoolExecutor(10).map(like, range(10)))
httpx.get("http://127.0.0.1:8000/notices/1").json()["likes"]   # 10이 올랐나요?

자동 점검 도구와 견주기

진단을 어느 정도 마쳤으면 도구를 돌립니다. 도구를 먼저 돌리면 도구가 찾은 것에만 눈이 가서, 도구가 못 찾는 약점을 놓치기 쉽습니다.

bandit -r app.py
pip-audit -r requirements.txt
확인할 것내 결과
bandit이 보고한 결과 수
bandit 결과 가운데 내 진단표에 이미 있던 것
bandit 결과 가운데 새로 진단표에 옮긴 것
bandit 결과 가운데 오탐으로 판정한 것과 이유
pip-audit이 보고한 패키지

도구 결과를 진단표에 옮길 때는 S11-P37-03에서처럼 근거를 확인한 뒤에 옮깁니다. 도구가 보고한 규칙 번호(예: B602)와 CWE 번호를 진단 근거에 함께 적어 두면 나중에 찾아보기 좋습니다.

생각해 보기. 내 진단표에는 있는데 bandit은 보고하지 않은 약점을 세 가지 골라 보세요. bandit이 왜 못 찾았을까요?
