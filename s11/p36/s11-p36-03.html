동시 대여 경쟁 조건 재현

S6에서 "동시에 빌리면 1권뿐인 책이 두 번 빌려질 수 있다"고 경고만 하고 넘어갔습니다. 이번에는 Docker Compose로 띄운 PostgreSQL 환경에서 10명이 동시에 대여해 이 문제를 눈으로 확인합니다.

문제가 되는 코드

현재 대여 서비스는 재고를 확인한 뒤, 메모리에 읽어 둔 값으로 재고를 계산해 저장합니다.

app/services/books.py
def change_stock(db: Session, book: Book, change: int, reason: str) -> None:
    """재고를 바꾸고 기록을 남깁니다. 확정(commit)은 이 함수를 부른 쪽에서 합니다."""
    if book.stock + change < 0:
        raise AppError(409, "INSUFFICIENT_STOCK", f"재고가 부족합니다. 현재 재고는 {book.stock}권입니다.")
    book.stock += change
    book_repo.add_stock_log(db, book, change, reason)

book.stock += change는 "지금 데이터베이스의 재고에서 1을 빼라"가 아니라 "내가 읽었던 재고(1)에서 1을 뺀 값(0)을 저장하라"는 뜻입니다. 실제로 데이터베이스에 가는 문장은 UPDATE books SET stock=0 WHERE id=7입니다. 10명이 모두 재고 1을 읽었다면 10명 모두 "재고를 0으로" 저장하고 대여에 성공합니다. 재고는 0으로 멀쩡해 보이지만 대여 기록은 10건이 됩니다. 앞선 변경이 뒤의 변경에 덮여 사라졌다는 뜻에서 이 현상을 갱신 손실(lost update)이라고 부릅니다.

재현 준비

컴퓨터가 빠르면 확인과 변경 사이의 틈이 아주 짧아 문제가 잘 나타나지 않습니다. 실습에서는 틈을 일부러 0.2초로 벌립니다. 이 줄은 확인이 끝나면 반드시 지웁니다.

동시에 요청을 보낼 프로그램을 tools/race_test.py로 만듭니다. 10명이 먼저 로그인해 둔 뒤, 스레드 10개로 대여 요청을 한꺼번에 보냅니다. 스레드는 한 프로그램 안에서 동시에 실행되는 작업 단위입니다.

tools/race_test.py
"""동시 대여 시험: 재고가 1권인 도서를 10명이 동시에 빌립니다. 사용법: python tools/race_test.py 도서번호"""
import sys
from concurrent.futures import ThreadPoolExecutor

import httpx

BASE_URL = "http://127.0.0.1:8000"
BOOK_ID = int(sys.argv[1])
PASSWORD = "race-test-pass-1"


def login(i: int) -> dict:
    email = f"race{i}@example.com"
    httpx.post(f"{BASE_URL}/auth/signup", json={"email": email, "password": PASSWORD})  # 이미 있으면 409, 무시
    token = httpx.post(f"{BASE_URL}/auth/token", data={"username": email, "password": PASSWORD}).json()["access_token"]
    return {"Authorization": f"Bearer {token}"}


def borrow(headers: dict) -> int:
    return httpx.post(f"{BASE_URL}/loans", json={"book_id": BOOK_ID}, headers=headers, timeout=30).status_code


users = [login(i) for i in range(10)]           # 먼저 10명이 모두 로그인해 둡니다.
with ThreadPoolExecutor(max_workers=10) as pool:  # 10개의 요청을 한꺼번에 보냅니다.
    results = list(pool.map(borrow, users))

print("응답 상태:", results)
print("대여 성공(201):", results.count(201))
print("남은 재고:", httpx.get(f"{BASE_URL}/books/{BOOK_ID}").json()["stock"])

왜 PostgreSQL에서 재현하나요

개발용 SQLite는 한 번에 한 요청만 쓰기를 하도록 데이터베이스 전체를 잠그기 때문에 이 문제가 다른 모습(잠금 오류나 대기)으로 나타납니다. 운영 환경과 같은 PostgreSQL로 재현해야 실제로 일어날 일을 볼 수 있습니다. S8에서 만든 Compose 환경을 그대로 씁니다.

재고 숫자만 보면 아무 문제가 없어 보인다는 점이 이 버그를 더 위험하게 만듭니다. 1권뿐인 책을 10명이 빌렸고, 반납이 시작되면 재고는 10권으로 늘어납니다. 재고 기록(stock_logs)의 합계와 실제 재고도 서로 맞지 않게 됩니다.

KISA 구현 단계의 시간 및 상태 유형, 검사 시점과 사용 시점(TOCTOU)의 경쟁 조건입니다. OWASP API Security Top 10 2023에서는 API6(민감한 업무 흐름에 대한 제한 없는 접근)과 관련이 있습니다. 공격자가 일부러 동시에 요청을 보내 한정된 재고나 쿠폰을 여러 번 가져가는 공격으로 이어질 수 있습니다.
