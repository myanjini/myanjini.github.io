보안 그룹과 네트워크 ACL

서브넷과 라우팅이 "길이 있느냐"를 정한다면, 방화벽은 "그 길로 누구를 들여보내느냐"를 정합니다. AWS의 방화벽은 보안 그룹과 네트워크 ACL 두 가지입니다.

보안 그룹

보안 그룹은 EC2, RDS 같은 자원 하나하나에 붙이는 방화벽입니다. 규칙에는 허용만 적고, 적지 않은 것은 모두 막힙니다.

특징뜻
허용 규칙만"이 포트를, 이곳에서 오는 요청에 허용"만 적습니다. 거부 규칙은 없습니다.
기본값새로 만들면 인바운드(들어오는 요청)는 모두 막히고, 아웃바운드(나가는 요청)는 모두 허용됩니다.
상태 저장(stateful)들어온 요청에 대한 응답은 아웃바운드 규칙과 관계없이 나갈 수 있습니다. 반대로 내가 보낸 요청의 응답도 자동으로 들어옵니다.
출처로 보안 그룹 지정출처에 IP 범위 대신 다른 보안 그룹을 적을 수 있습니다. "이 보안 그룹이 붙은 자원에서 오는 요청만"이라는 뜻입니다.

마지막 특징이 특히 중요합니다. DB 보안 그룹의 출처를 "API 서버의 보안 그룹"으로 적으면, API 서버의 IP가 바뀌거나 서버가 늘어나도 규칙을 고칠 필요가 없고, 그 밖의 어떤 자원도 DB에 닿을 수 없습니다.

예: DB 보안 그룹 인바운드프로토콜과 포트출처뜻
좋은 규칙TCP 5432book-api-sg(보안 그룹)API 서버에서 오는 PostgreSQL 연결만
나쁜 규칙TCP 54320.0.0.0/0인터넷 어디서든 DB 비밀번호 대입 시도 가능
나쁜 규칙모든 트래픽10.0.0.0/16VPC 안의 아무 자원이나 모든 포트로

네트워크 ACL

네트워크 ACL은 서브넷 단위로 걸리는 방화벽입니다. 보안 그룹과 성격이 다릅니다.

보안 그룹네트워크 ACL
적용 단위자원(네트워크 인터페이스)서브넷
규칙허용만허용과 거부, 번호 순서대로 평가
상태상태 저장: 응답은 자동 허용상태 비저장: 응답이 나가는 포트까지 따로 허용해야 함
기본값인바운드 모두 거부기본 ACL은 모두 허용
주로 쓰는 곳자원마다 세밀한 접근 제어특정 IP 대역을 서브넷 전체에서 막는 굵은 제어

네트워크 ACL은 상태를 기억하지 않으므로, 응답이 돌아가는 임시 포트(1024~65535)까지 생각해 규칙을 짜야 해서 실수하기 쉽습니다. 이 과정에서는 기본 ACL(모두 허용)을 그대로 두고 보안 그룹으로 접근을 제어합니다. 대부분의 서비스도 같은 방식으로 운영합니다.

API 서버의 보안 그룹에 인바운드 규칙 "TCP 8000, 내 IP"만 있습니다. API 서버가 PyPI에서 패키지를 내려받을 수 있나요?

인바운드 규칙은 "밖에서 먼저 들어오는 요청"에만 적용됩니다. 서버가 먼저 보낸 요청의 응답은 보안 그룹이 기억하고 들여보냅니다(기본 네트워크 ACL은 모두 허용).
