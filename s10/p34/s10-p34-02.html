로그인 시도 제한

로그인 실패를 기록하고, 일정 시간 안에 너무 많이 실패하면 잠시 막습니다. 계정 기준과 IP 기준을 함께 쓰는 이유와 설계를 강사 화면으로 봅니다.

설계

결정값과 이유
계정 기준15분 안에 같은 이메일로 5번 실패하면 막습니다. 한 계정을 노리는 무차별 대입을 막습니다.
IP 기준15분 안에 같은 IP에서 20번 실패하면 막습니다. 여러 계정을 돌아가며 시도하는 스프레이를 막습니다.
응답429 Too Many Requests와 Retry-After: 900 헤더(몇 초 뒤에 다시 시도할지)
검사 시점비밀번호를 확인하기 전에 검사합니다. 잠긴 동안에는 맞는 비밀번호를 넣어도 429여서, 공격자가 맞혔는지 알 수 없습니다.
없는 계정가입하지 않은 이메일의 실패도 기록하고 똑같이 막습니다. 다르게 처리하면 가입 여부가 드러납니다(S5-P16).
성공하면그 계정의 실패 기록을 지웁니다.
저장 위치데이터베이스. 서버 메모리에 두면 서버를 여러 대로 늘렸을 때(8일차) 서버마다 따로 세게 됩니다.

class LoginFailure(Base):
    """로그인 실패 기록. 일정 시간 안의 실패 횟수를 세는 데 씁니다."""

    __tablename__ = "login_failures"

    id: Mapped[int] = mapped_column(primary_key=True)
    email: Mapped[str] = mapped_column(String(255), index=True)
    ip: Mapped[str] = mapped_column(String(45), index=True)  # IPv6 주소까지 담을 수 있는 길이
    created_at: Mapped[datetime] = mapped_column(index=True)
app/services/login_guard.py
"""로그인 시도 제한: 계정과 IP마다 일정 시간 안의 실패 횟수를 셉니다."""
from datetime import datetime, timedelta, timezone

from sqlalchemy.orm import Session

from app.errors import AppError
from app.repositories import login_failures as failure_repo

WINDOW = timedelta(minutes=15)   # 이 시간 안의 실패만 셉니다.
MAX_FAILURES_PER_EMAIL = 5       # 한 계정에 대한 실패 허용 횟수
MAX_FAILURES_PER_IP = 20         # 한 IP에서의 실패 허용 횟수(여러 계정을 돌아가며 시도하는 공격 대비)


def check_allowed(db: Session, email: str, ip: str) -> None:
    """실패가 너무 많으면 비밀번호를 확인하기 전에 429로 막습니다."""
    since = datetime.now(timezone.utc) - WINDOW
    if (failure_repo.count_since(db, since, email=email) >= MAX_FAILURES_PER_EMAIL
            or failure_repo.count_since(db, since, ip=ip) >= MAX_FAILURES_PER_IP):
        raise AppError(429, "TOO_MANY_ATTEMPTS", "로그인 시도가 너무 많습니다. 15분 뒤에 다시 시도하세요.",
                       headers={"Retry-After": str(int(WINDOW.total_seconds()))})


def record_failure(db: Session, email: str, ip: str) -> None:
    failure_repo.add(db, email, ip, datetime.now(timezone.utc))
    db.commit()


def reset(db: Session, email: str) -> None:
    """로그인에 성공하면 그 계정의 실패 기록을 지웁니다. 확정은 토큰 발급과 함께 합니다."""
    failure_repo.clear(db, email)
app/routers/auth.py
@router.post("/token", response_model=Token, summary="로그인(토큰 발급)",
             responses={401: {"description": "이메일 또는 비밀번호가 틀림"},
                        429: {"description": "로그인 시도가 너무 많음"}})
def login(request: Request, db: SessionDep, form: Annotated[OAuth2PasswordRequestForm, Depends()]):
    # OAuth2 규칙상 입력 칸 이름은 username입니다. 이 앱에서는 이메일을 넣습니다.
    email = form.username.lower()
    ip = request.client.host if request.client else "unknown"
    login_guard.check_allowed(db, email, ip)
    user = authenticate(db, email, form.password)
    if user is None:
        login_guard.record_failure(db, email, ip)
        logger.warning("로그인 실패")  # 입력한 이메일과 비밀번호는 로그에 남기지 않습니다.
        raise AppError(401, "INVALID_CREDENTIALS", "이메일 또는 비밀번호가 올바르지 않습니다.", headers=BEARER)
    login_guard.reset(db, email)
    return issue_tokens(db, user)

request.client.host는 요청을 보낸 쪽의 IP입니다. 8일차에 로드 밸런서 뒤에 서버를 두면 모든 요청이 로드 밸런서의 IP로 보이므로, 로드 밸런서가 붙여 주는 원래 IP 헤더를 믿도록 uvicorn을 설정해야 합니다.

한계대응
공격자가 남의 계정을 일부러 잠글 수 있습니다.잠금 시간을 짧게(15분) 하고, 영구 잠금은 하지 않습니다. 이메일 인증이나 CAPTCHA를 더하기도 합니다.
회사나 학교처럼 많은 사람이 IP 하나를 함께 씁니다.IP 기준 한도를 계정 기준보다 넉넉하게 둡니다.
IP를 계속 바꾸는 공격(봇넷)애플리케이션만으로는 어렵습니다. 앞단의 WAF와 함께 막습니다(S10-P34-04).
실패 기록이 계속 쌓입니다.오래된 기록을 정기적으로 지우는 작업을 둡니다.
