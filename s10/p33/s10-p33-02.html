하드코딩된 비밀정보 찾기

코드에 비밀 값을 직접 적는 것을 하드코딩이라고 합니다. 지금 코드에 없더라도 예전에 적었다가 지운 적이 있다면 Git 이력에 그대로 남아 있습니다.

비밀 값이 숨는 곳

위치예
코드SECRET_KEY = "k9Xq2...", 테스트 코드의 실제 계정 비밀번호
설정 파일compose.yaml, Dockerfile의 ENV, alembic.ini의 데이터베이스 주소
Git 이력지금은 지웠지만 예전 커밋에 들어 있는 값
터미널 기록docker run -e SECRET_KEY=...처럼 명령에 직접 적은 값
CI 기록과 로그실행 중에 출력한 환경 변수, 오류 메시지 속 접속 정보

지금 코드에서 찾기

git grep은 Git이 관리하는 파일 안에서만 찾으므로 .venv 같은 폴더를 건너뜁니다.

git grep -n -i -E "secret|password|token|api_key"

결과가 많이 나오지만 대부분은 변수 이름이나 설명입니다. 하나씩 보며 값이 직접 적힌 줄만 골라냅니다. 테스트 전용 키처럼 비밀이 아닌 값도 있으므로 사람이 판단합니다.

Git 이력에서 찾기

한 팀원이 처음에 비밀 키를 코드에 적어 커밋했다가, 다음 커밋에서 환경 변수로 바꿨다고 합시다. 지금 파일에는 값이 없지만 이력을 검색하면 나옵니다.

git log -p -S "hardcoded-secret" --oneline
d6169ae use env var
-SECRET_KEY = "k9Xq2-hardcoded-secret-value-1234567890"
+import os
+SECRET_KEY = os.environ["SECRET_KEY"]
383e2b0 add config
+SECRET_KEY = "k9Xq2-hardcoded-secret-value-1234567890"

-S는 그 글자가 추가되거나 지워진 커밋을 찾습니다. 저장소를 받은 사람이면 누구나 이렇게 찾을 수 있습니다. 실무에서는 gitleaks 같은 도구로 이력 전체를 자동으로 검사하고, GitHub도 비밀 값으로 보이는 문자열이 푸시되면 막거나 알려 주는 기능(secret scanning, push protection)을 제공합니다.

노출된 비밀 값은 바꿉니다

이력에서 지우는 것만으로는 부족합니다. 이미 누군가 저장소를 복제했을 수 있습니다. 한 번 노출된 비밀 값은 새어 나간 것으로 보고 교체하는 것이 원칙입니다.

순서SECRET_KEY가 노출되었을 때
1secrets.token_urlsafe(32)로 새 키를 만듭니다.
2서버의 환경 변수(7일차부터는 Parameter Store)를 새 값으로 바꾸고 다시 시작합니다. 그 순간 예전 키로 서명된 액세스 토큰은 모두 무효가 됩니다.
3공격자가 이미 받아 둔 리프레시 토큰이 있을 수 있으면 refresh_tokens를 모두 revoked로 바꿔 전원 다시 로그인하게 합니다(S5-P18-04).
4코드와 이력에서 값을 지우고, 같은 일이 다시 없도록 점검 도구를 CI에 넣습니다(6일차).
5노출 기간 동안 이상한 로그인이나 요청이 있었는지 로그를 확인합니다.
